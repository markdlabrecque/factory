# Sandcastle setup (layers)

> **Experimental, not supported:** interactive agents under herdr-core are research only; see `docs/research/interactive-agents-herdr-core.md`. Do not add them to a project setup.

When copying the workflow, use the shipped `board/` files.

When setting up scheduler tests or verification, read `TESTING.md` in the helper repository. Use stubbed service-manager commands for automated verification; real systemd trials are optional and require operator approval.

When developing this helper repository, follow its `AGENTS.md` and hand implementation to Factory through prepared tickets. For the planned self-recovery slice, read `docs/slice-4/plan.md` in the helper repository for the agreed decisions and manual-upgrade scope; `docs/factory-cli.md` contains the high-level requirements. Its repair prompt (`orchestrator/prompt.recover.md`, used by `main.mts --recover`) is not a setup asset yet: do not install it until the reviewed recovery upgrade exists. `recovery.mts` and `recovery-sandbox.mts` are part of the workflow `factory init` copies, because `main.mts` imports them; both are import-safe, so ordinary dispatch is unaffected, and recovery stays inactive without the prompt.

Sandcastle has no built-in GitLab tracker (maintainer points to `Custom`; upstream #511, #521). Instead of improvising from `SETUP_ISSUE_TRACKER.md`, apply fixed layers from `layers/`. The scaffold is copied into the project, so no fork of Sandcastle is needed.

## Factory-managed board

If the user chooses the Factory CLI, follow the repository README's "Install the Factory CLI" section instead of running the legacy board installers. Set `SANDCASTLE_STATE_DIR=$HOME/.local/state/factory` for project dispatchers. Confirm `factory board status` is active and `factory doctor` reports a responding board. The CLI now scaffolds the minimal workflow (`factory init`) and, on Linux, schedules passes (`factory schedule on --project <name>`, then `factory schedule on`; see the README's "On a schedule: `factory schedule`"). `factory schedule off` stops the timer and cancels the tick in progress, and `factory install` over an existing install leaves the timer disabled until you run `schedule on` again, so don't also install `install-dispatch.sh` timers for that project. A machine that already has them moves over by hand with the repository's `docs/scheduler-cutover.md`. Pass and tick timings are kept in `~/.local/state/factory/scheduler/history.json` (the last 1000). It does not provision environments, so keep following this skill for those. If an old Sandcastle board uses port 4444, ask the user to stop it before installing Factory. The CLI warns about old services without changing them.

`factory init` (CLI slice two) now adds the minimal workflow files (the **Workflow** step below, minus environment specifics) and `factory project add` registers a checkout; both leave existing files untouched. This skill still owns the tracker/agent layers, the Dockerfile, the optional Docker, CMS, web-runtime, ddev and Playwright layers, and adapting prompts and `sandboxSetup` to the stack. `.sandcastle` is kept; migration to `.factory` belongs to a later slice (`docs/factory-cli.md`). The personal profile maps `model:sonnet` and `model:opus` to `pi-claude-subscription/claude-sonnet-5-5` and `pi-claude-subscription/claude-opus-5-5` (Opus verifies, Sonnet analyses); see "Agent: Pi" below for the sandbox side.

## Detect (defaults; confirm with the user, don't ask from scratch)
Inspect the project root first and propose these as the answers:
- **Drupal:** `composer.json` requires `drupal/core`, `drupal/core-recommended` or `drupal/cms`, or `web/core/` / `docroot/core/` exists. Docroot is the dir holding `core/` (usually `web/`). Layers: web + Drupal + Playwright.
- **WordPress:** `wp-config.php`, `wp-content/` or `wp-includes/` at the root or in `web/`/`public/`/`wp/`, or `composer.json` requires `johnpbloch/wordpress*` or `roots/wordpress*`. Docroot is the dir holding `wp-config.php` (or `wp-load.php`). Layers: web + WordPress + Playwright.
- **PHP_VERSION:** `.ddev/config.yaml` `php_version`, else `composer.json` `config.platform.php`, else the minor from `require.php`, else 8.3. Use the minor only (`8.3`).
- **Both or neither matched:** ask. Not a PHP/web project: offer tracker layer only.
- **ddev in tests:** if project tests or scripts call `ddev drush|wp|composer|exec`, propose the ddev shim layer. The host keeps DDEV; only the sandbox bypasses it.
- **Tracker:** the GitLab layer is the default when `git remote get-url origin` points at a GitLab host (e.g. git.affinitybridge.com); use that host as `GITLAB_HOST`.
- **Flavour:** a GitHub remote means a personal project: GitHub tracker layer, Pi agent layer (`sandcastle init` with agent **Pi**), and the workflow's `config.personal.mts`. A GitLab remote means client work: GitLab layer, Claude Code, and `config.mts`.
Report what was detected and why (which file matched) in one line, then confirm.

**Database:** MariaDB for both Drupal and WordPress (decided 2026-11-05). SQLite deferred: Drupal supports it natively, WordPress needs the SQLite Database Integration plugin, and prod dumps are MySQL-shaped.

| --- | --- | --- |
| Tracker: GitLab | `layers/tracker-gitlab/` | `GITLAB_HOST` (default git.affinitybridge.com), `LABEL` (default `Sandcastle`; only for the init template's prompt, see Base install step 3), `GLAB_VERSION` |
| Tracker: GitHub | `layers/tracker-github/` | `LABEL` (as for GitLab), `GH_VERSION` |
| Agent: Pi | `layers/agent-pi/` | `PI_VERSION` (npm `@earendil-works/pi-coding-agent`); replaces the init template's deprecated `@mariozechner/pi-coding-agent` line. | Compat: ddev shim | `layers/compat-ddev/` | web runtime; add when the project's scripts or tests shell out to `ddev` (`grep -rl 'ddev ' tests/ scripts/`) |

## Steps

### Base install (always)
1. Run **Detect** above and confirm the values. Check the branch is clean. If `.sandcastle/` doesn't exist, `npx sandcastle init` with tracker **Custom** and the **Docker** provider (always Docker, not Podman).
2. **Fail loudly if the scaffold moved.** Grep `.sandcastle/` for `No issue tracker configured`, `<view command`, `<close command`, `TODO: install your issue tracker`. If any is missing, stop and say which.
3. Tracker layer: substitute list/view/close from `tracker-gitlab/commands.md` for the markers. These markers live in the init template's own `prompt.md` and `main.mts` (e.g. `simple-loop`); `LABEL` only filters that template's issue list. Use the default and don't ask about it, create it, or reconcile it with anything: if the workflow is chosen later, its files replace these and its labels come from `config.mts`. Put `.env` lines from `env.snippet` into `.sandcastle/.env` and `.env.example`; **leave `GITLAB_TOKEN` empty, tell the user to fill it** (never fetch it from 1Password). Replace the Dockerfile's `# TODO: install your issue tracker's CLI` line with `glab.Dockerfile.snippet`.
   GitHub: the same with `tracker-github/` (`gh.Dockerfile.snippet`, `GH_TOKEN` left empty). With Pi, swap the template's pi install line for `agent-pi/pi.Dockerfile.snippet`, drop the template's `ANTHROPIC_API_KEY` line from `.env.example`, and, for the personal config, install the provider on the host (`git clone --depth 1 --branch <tag> https://github.com/markdlabrecque/pi-claude-subscription.git ~/.pi/agent/extensions/pi-claude-subscription && cd ~/.pi/agent/extensions/pi-claude-subscription && npm ci --omit=dev --ignore-scripts`), run `claude auth login`, and run `.sandcastle/dispatch.sh --dry-run` (its preflight checks the provider, the login and the token). Do not use an OpenAI login for this config. Keep `.env`'s `CLAUDE_CODE_OAUTH_TOKEN` for the human to fill.
4. Verify: `glab auth status --hostname <host>` or `gh auth status`.

### Then ask: two separate questions
Once the base install is done, ask the user, as two separate yes/no questions (not one combined question):
1. **Docker setup?** Adds the web runtime, CMS and Playwright layers that Detect proposed, so agents can run and check the site.
2. **Workflow?** Adds the sandcastle-helper workflow: the one-ticket orchestrator (implement, verify with evidence, MR), the dispatcher with its ticket graph (it claims each launch against the shared run cap and the ticket, atomically under a lock, before it spawns it), and the board.

The workflow's verifier needs the web runtime and Playwright. If the user wants the workflow but declines the Docker setup and the image doesn't already have those layers, say so and ask again before going on. Do whichever parts they chose, Docker first.

### Docker setup (if chosen)
1. Add the chosen `*.Dockerfile.snippet` files after the glab one, in order: web, CMS, ddev shim, Playwright. Copy `runtime-web/start-web.sh` (and `compat-ddev/ddev-shim.sh` with the shim) into `.sandcastle/` (the snippets COPY them; they must be in the build context).
2. Web layer hook: `start-web.sh <detected docroot>` run as root once the sandbox is ready. With the workflow, it goes in `CONFIG.sandboxSetup` in `main.mts` (`{ command: "start-web.sh <docroot>", sudo: true }`); without it, add `hooks: { sandbox: { onSandboxReady: [{ command: "start-web.sh <docroot>", sudo: true }] } }` to the init template's `main.mts`. Project code reaches Playwright's global install via `NODE_PATH=$(npm root -g)` (ESM ignores it; use CJS or install `playwright` in the project).
3. Verify: build the image (`npx sandcastle docker build-image`); a `maxIterations: 1` run on a throwaway ticket where the agent starts the web layer, loads the page with Playwright, and closes the ticket.
4. Prompt conventions (the init template's prompt; skip with the workflow, which ships its own): state the label; commit messages start with the ticket ref (`#425: ...`); `glab mr create` titles start `#<iid>: `; tell the agent to check its work with the web server and Playwright before committing.

### Workflow (if chosen)
Source: a sandcastle-helper checkout. Ask for its path (default `~/Projects/sandcastle-helper`); if there is none, `gh repo clone markdlabrecque/sandcastle-helper` into a temp dir. Follow its `orchestrator/ADAPTING.md` ("Install into a project" and "What to adapt per project"):
1. Prefer `factory init` (adds the missing files, never overwrites). Otherwise copy the files ADAPTING.md lists into `.sandcastle/`, overwriting the init template's `main.mts` and `prompt.md` (the base install's list/close substitutions and `LABEL` go with them; the workflow's host-side code does that work with the host's `glab` login, so `GITLAB_TOKEN` in `.env` stays unused). Delete the template's other prompt files if it shipped any.
2. Fill in `config.mts` (for a personal project, `factory init --profile personal` or copying `config.personal.mts` over it sets `TRACKER.project` to `owner/repo`; its models and model labels stay as shipped: `model:sonnet`, `model:opus`): GitLab host, project path and numeric id (`glab api projects/<url-encoded path>`), and the milestone (ask which; unset means every open ticket in the project). Labels: show the shipped `LABELS` (ready, exclude, needs-human, and done: the stage a ticket moves to once merged, default `Internal QA`) and ask once whether to keep them. `SUBTASKS.enabled` (one run per GitLab Task) stays on unless the user says otherwise. Don't bring the base install's `LABEL` into this.
3. Set `CONFIG.image` in `main.mts` to this project's image, and put the web hook in `CONFIG.sandboxSetup` (see Docker setup step 2).
4. Adapt `sandbox/bootstrap-site.sh`, the Environment section of `prompt.md`, and `prompt.verify.md` to this project's stack. The shipped `bootstrap-site.sh` is Drupal-only; WordPress needs a new one that ends with the site answering on `http://127.0.0.1`.
5. Add `@ai-hero/sandcastle` and `tsx` as dev dependencies, and `evidence/`, `state/`, `logs/` and `board.html` to `.sandcastle/.gitignore`. The host needs Node 22.18+, and `glab` and `claude` (or `gh` and `pi`) logged in.
   For HTTP evidence previews, install the board service using `board/install-service.sh` or `board/install-launchd.sh`. Keep `board.mts`, `board-server.mts` and `board.template.html` together when updating it. Board and evidence share one Factory design, sticky navigation and an Appearance panel that saves the mode (light, dark, system). The HTTP board polls the service's read-only `/api/runs` every 10s and animates changes in place (no reloads; reduced motion respected). Evidence opens in the same tab, with media/text previews and a link back to the board. Text previews stop at 64 KiB; originals remain available. Evidence pages never poll. Without the service, local `board.html` opens evidence folders directly.
6. Verify: with the integration branch checked out, `.sandcastle/dispatch.sh --dry-run` (or, for a project registered with the Factory CLI, `factory dispatch --dry-run`; `factory run <ticket>` or `dispatch.sh --issue <ticket>` runs one ticket in the foreground after the same checks; `factory retry <ticket>` clears a failed run so the next pass picks it up; `factory status` shows the board service, scheduler health and timings, and each run's stage; `factory logs [ticket] [-f]` shows a run's log; see "Running work" in the sandcastle-helper README) from a terminal (it builds the image if it's missing) and show the user the output. It checks the labels exist; ask before letting it create any.
