# Sandcastle setup (layers)

The Factory checkout's `.pi/settings.json` sets `defaultProvider` to `openai` for interactive Pi use. Configure orchestrator models separately; this is not a scaffold model setting.

For GitHub setup, check [verification media prerequisites and failure handling](../../README.md#github-tooling) before enabling runs. The host needs `gh` 2.99.0+ with `issue comment --attach` and repository push access on a supported GitHub.com or Enterprise Cloud host. Factory's runtime uses plain `gh`; interactive agents use `gh-axi` except for attachment uploads. Normal and recovery runs post one native attachment-bearing verification comment for every verdict, including with `--no-push`. Upload failures retain local evidence and stop delivery without an evidence-branch fallback; existing evidence links stay untouched. Review existing project copies before updating them. For token and rendering details, read [media upload research and live verification](../../docs/research/github-media-uploads.md).

> **Experimental, not supported:** interactive agents under herdr-core are research only; see `docs/research/interactive-agents-herdr-core.md`. Do not add them to a project setup.

When copying the workflow, use the shipped `board/` files. Skip `board/board-prototype.html` if present. It is an experimental, simulated-data design lab, not a scaffold or install input. For its dot trackers with centered connectors, solid green/red current dots with soft halos and sonar pulses that freeze on Pause and hide with reduced motion, queue-reason rules, Shipped history, ticket stats, demo controls and themes, read the helper README's [Board design lab](../../README.md#board-design-lab-prototype-branch-only) section. This prototype replaces Assembly and Megastructure. Its approved tracker design now powers the supported `board.template.html`; only the prototype file is excluded from installation. Both changes were made directly with human approval, without Factory.

When setting up scheduler tests or verification, read `TESTING.md` in the helper repository. Use stubbed service-manager commands for automated verification; real systemd trials are optional and require operator approval. Read-only stubs must leave shared state byte-identical because timer queries run concurrently. Run CI with TAP failure details and a bounded test deadline rather than waiting for the job limit. Synchronize process fixtures instead of assuming immediate exit or signal delivery, and register all descendant cleanup before assertions.

When developing this helper repository, follow its `AGENTS.md` and hand implementation to Factory through prepared tickets. For the planned self-recovery slice, read `docs/slice-4/plan.md` in the helper repository for the agreed decisions and manual-upgrade scope; `docs/factory-cli.md` contains the high-level requirements. Its repair prompt (`orchestrator/prompt.recover.md`, used by `main.mts --recover`) is copied by `factory init` with `recovery.mts` and `recovery-sandbox.mts` (#63). Recovery is active only while the copy's recovery workflow is complete and unchanged since its review. `factory init` records the review for a new scaffold. Editing `main.mts` (for example `sandboxSetup`), `prompt.verify.md` or another workflow file turns recovery off until `factory recovery review --confirm --project <name>`. When you finish setting up a project, tell the developer to run that command. For an existing project, follow "Upgrading an existing project for self-recovery" in `orchestrator/ADAPTING.md`; never copy the files over customizations or record the review yourself. A scheduled pass of a current `dispatch.mts` also writes a jam report the Factory scheduler counts (#61); keep `dispatch.mts` and `graph.mts` together when updating a copy. Until the workflow is complete and reviewed, a confirmed jam is only recorded, never repaired.

Sandcastle has no built-in GitLab tracker (maintainer points to `Custom`; upstream #511, #521). Instead of improvising from `SETUP_ISSUE_TRACKER.md`, apply fixed layers from `layers/`. The scaffold is copied into the project, so no fork of Sandcastle is needed.

## Factory configuration

For a new/empty workflow, use `factory init --profile personal|client`; review the
commented `.sandcastle/factory.toml`. It owns tracker, agent/model aliases, labels,
selection, work units, dispatch, merge, graph, CI and sandbox startup steps. Read
[the complete v1 schema/defaults, tracker capabilities and migration mapping](../../docs/project-config.md)
before changing settings. Present TOML is authoritative with **no legacy per-field
fallback**. Unknown/invalid keys and unsupported tracker options fail before
credentials, Docker/npm, tracker mutation or admission. Without TOML, legacy
config/SELECT/CONFIG customizations keep working.

Do not silently migrate an existing scaffold: init repair skips TOML if workflow
files already exist; update never creates or overwrites it. Have the human review
main/dispatch/shell, tracker/refresh/preflight and runtime/selection helpers together,
including all `vendor/smol-toml/` ESM files, package scope and BSD-3-Clause license.
Preserve the parser's upstream bytes; `.gitattributes` exempts only generated vendor JS
from trailing-space checks. Transcribe
all settings manually; adding TOML to old code is insufficient. Reconfirm recovery
review for upgraded executable helpers. Do not fetch credentials, contact production
or auto-enable scheduling. Keep scripts/prompts, `.env`, registry and scheduler
files separate. Startup commands are trusted project code run inside the sandbox;
TOML is not a security boundary. Both new profiles retain empty setup.

Use `factory selection explain <ticket> [--project <name|path>] [--json]` for read-only
validation: config source, effective selection/work/dispatch with explicit/default
sources, eligibility/reasons, and separate historical execution holds. Missing/stale
holds are unknown; eligibility does not imply admission. It writes no state, calls
no analysis/ensureLabels and starts no work. Exit 0 is evaluated eligible/excluded;
exit 1 is invalid config, failed retrieval or unknown. JSON fields are `source`,
`settings`, `eligibility`, `reasons`, `executionHolds`. Legacy SELECT explanation is
unsupported/unknown without executing project config or main/dispatch.

## Factory-managed board

Set the scheduled concurrency cap at `[dispatch] max_concurrent` in `factory.toml`
(legacy-only: `SELECT.maxConcurrent` in `dispatch.mts`). CLI `--max` overrides must
be positive safe integers; invalid caps fail before shell preflight. Scheduled passes send no `--max` override and count active runs and launch reservations across all projects from the shared board. Manual `factory dispatch --max N` still overrides the config for that pass.

If the user chooses the Factory CLI, follow the repository README's "Install the Factory CLI" section (`factory clean` there removes a project's merged, clean local Factory branches and worktrees, and the scheduler runs it after each completed scheduled pass; remote branches are never touched) instead of running the legacy board installers. Set `SANDCASTLE_STATE_DIR=$HOME/.local/state/factory` for project dispatchers. To update an install, pull the Factory checkout and run `factory install` from inside it; the installed command run elsewhere refuses rather than reinstall its own copy. Then, in each project, run `factory update --dry-run` and `factory update --apply` to bring its `.sandcastle/` copy current; merge the edited and project-owned files it lists by hand, and run `factory recovery review --confirm` if it says a recovery workflow file changed. Install leaves the scheduler off; when it prints the resume reminder, run `factory schedule on` if the user wants scheduled passes back. Confirm `factory board status` is active and `factory doctor` reports a responding board. The CLI now scaffolds the minimal workflow (`factory init`) and, on Linux, schedules passes (`factory schedule on --project <name>`, then `factory schedule on`; see the README's "On a schedule: `factory schedule`"). `factory schedule off` stops the timer and cancels the tick in progress, and `factory install` over an existing install leaves the timer disabled until you run `schedule on` again, so don't also install `install-dispatch.sh` timers for that project. A machine that already has them moves over with the repository's `docs/scheduler-cutover.md`: `factory legacy status` lists them and `factory legacy retire` disables them (ask the user before running it). Pass and tick timings are kept in `~/.local/state/factory/scheduler/history.json` (the last 1000). Manual ticket comments, verdict corrections and archive state are kept in `~/.local/state/factory/journal/` (#98; `factory ticket comment <ticket> <text>` saves a comment there and posts it with the host `gh`/`glab` login, and `factory ticket sync` posts any it could not, never twice; `factory ticket verdict <ticket> --verdict pass|fail --message <explanation>` saves one correction and posts it as a manual correction naming the previous/new verdict and run; failed posts stay local for sync. `factory ticket archive|restore <ticket>` hides/restores cards without deleting data or closing tracker issues, with repeats safe. The live board also has an X named "Archive ticket" on Shipped cards; it waits for server confirmation and shows failures inline. Its tooltip says run data, logs and evidence are preserved. Manual verdict badges say "corrected" with the original in a tooltip. Archive browsing and restore are command-only. Archive accepts only completed `done` history cards without active claims, never queued, waiting, stopped or active work. `ticket archived [--json]` lists them, and `ticket show <ticket> [--json]` includes original/effective verdict, archive state, history and pending/error delivery even while archived. All commands accept `--project <name|path>`), never in run records; don't edit or delete it when cleaning up state. It does not provision environments, so keep following this skill for those. If an old Sandcastle board uses port 4444, ask the user to stop it before installing Factory. The CLI warns about old services without changing them.

`factory init` (CLI slice two) now adds the minimal workflow files (the **Workflow** step below, minus environment specifics) and `factory project add` registers a checkout; both leave existing files untouched. This skill still owns the tracker/agent layers, the Dockerfile, the optional Docker, CMS, web-runtime and ddev layers, the standard Playwright layer, and adapting prompts and `sandboxSetup` to the stack. `.sandcastle` is kept; migration to `.factory` belongs to a later slice (`docs/factory-cli.md`). The personal profile maps description declarations `**Model:** Sonnet 5.5` and `**Model:** Opus 5.5` to `pi-claude-subscription/claude-sonnet-5-5` and `pi-claude-subscription/claude-opus-5-5` (Opus verifies, Sonnet analyses); see "Agent: Pi" below for the sandbox side.

## Detect (defaults; confirm with the user, don't ask from scratch)
Inspect the project root first and propose these as the answers:
- **Drupal:** `composer.json` requires `drupal/core`, `drupal/core-recommended` or `drupal/cms`, or `web/core/` / `docroot/core/` exists. Docroot is the dir holding `core/` (usually `web/`). Layers: web + Drupal + Playwright.
- **WordPress:** `wp-config.php`, `wp-content/` or `wp-includes/` at the root or in `web/`/`public/`/`wp/`, or `composer.json` requires `johnpbloch/wordpress*` or `roots/wordpress*`. Docroot is the dir holding `wp-config.php` (or `wp-load.php`). Layers: web + WordPress + Playwright.
- **PHP_VERSION:** `.ddev/config.yaml` `php_version`, else `composer.json` `config.platform.php`, else the minor from `require.php`, else 8.3. Use the minor only (`8.3`).
- **Both or neither matched:** ask. Not a PHP/web project: offer tracker layer only.
- **ddev in tests:** if project tests or scripts call `ddev drush|wp|composer|exec`, propose the ddev shim layer. The host keeps DDEV; only the sandbox bypasses it.
- **Tracker:** the GitLab layer is the default when `git remote get-url origin` points at a GitLab host (e.g. git.affinitybridge.com); use that host as `GITLAB_HOST`.
- **Flavour:** a GitHub remote means a personal project: GitHub tracker layer, Pi agent layer (`sandcastle init` with agent **Pi**), and `factory.personal.toml`. A GitLab remote means client work: GitLab layer, Claude Code, and `factory.client.toml`. Legacy config examples remain for migration only.
Report what was detected and why (which file matched) in one line, then confirm.

**Database:** MariaDB for both Drupal and WordPress (decided 2026-11-05). SQLite deferred: Drupal supports it natively, WordPress needs the SQLite Database Integration plugin, and prod dumps are MySQL-shaped.

## Steps

### Base install (always)
1. Run **Detect** above and confirm the values. Check the branch is clean. If `.sandcastle/` doesn't exist, `npx sandcastle init` with tracker **Custom** and the **Docker** provider (always Docker, not Podman).
2. **Fail loudly if the scaffold moved.** Grep `.sandcastle/` for `No issue tracker configured`, `<view command`, `<close command`, `TODO: install your issue tracker`. If any is missing, stop and say which.
3. Tracker layer: substitute list/view/close from `tracker-gitlab/commands.md` for the markers. These markers live in the init template's own `prompt.md` and `main.mts` (e.g. `simple-loop`); `LABEL` only filters that template's issue list. Use the default and don't ask about it, create it, or reconcile it with anything: if the workflow is chosen later, its files replace these and its labels come from `config.mts`. Put `.env` lines from `env.snippet` into `.sandcastle/.env` and `.env.example`; **leave `GITLAB_TOKEN` empty, tell the user to fill it** (never fetch it from 1Password). Replace the Dockerfile's `# TODO: install your issue tracker's CLI` line with `glab.Dockerfile.snippet`.
   GitHub: the same with `tracker-github/` (`gh.Dockerfile.snippet`, `GH_TOKEN` left empty). With Pi, swap the template's pi install line for `agent-pi/pi.Dockerfile.snippet`, drop the template's `ANTHROPIC_API_KEY` line from `.env.example`, and, for the personal config, install the provider on the host (`git clone --depth 1 --branch <tag> https://github.com/markdlabrecque/pi-claude-subscription.git ~/.pi/agent/extensions/pi-claude-subscription && cd ~/.pi/agent/extensions/pi-claude-subscription && npm ci --omit=dev --ignore-scripts`), run `claude auth login`, and run `.sandcastle/dispatch.sh --dry-run` (its preflight checks the provider, the login and the token). Do not use an OpenAI login for this config. Keep `.env`'s `CLAUDE_CODE_OAUTH_TOKEN` for the human to fill.
4. Verify: `glab auth status --hostname <host>` or `gh auth status`.

### Then ask: two separate questions
Once the base install is done, ask the user, as two separate yes/no questions (not one combined question):
1. **Docker setup?** Adds the standard Playwright layer and whichever web runtime and CMS layers Detect proposed, so agents can check the project.
2. **Workflow?** Adds the sandcastle-helper workflow: the one-ticket orchestrator (implement, verify with evidence, MR), the dispatcher with its ticket graph (it claims each launch against the shared run cap and the ticket, atomically in the admission record, before it spawns it), and the board. `factory init` copies `admission.mts`, `assessment.mts`, `journal.mts`, `refresh.mts` and `ownership.mts` with them. For an older project, run `factory update --dry-run` there first: it lists missing and outdated (unedited older) Factory files, files edited locally, and the project-owned `config.mts`, `main.mts`, `dispatch.sh`, `prompt.md` and `prompt.verify.md` to merge by hand, and writes nothing. Then copy `dispatch.mts`, `refresh.mts`, `analyze.mts`, `board.mts`, `assessment.mts` and the template together by hand, keeping `admission.mts` and `ownership.mts` beside their importers. `assessment.mts` and `journal.mts` are mandatory `board.mts` imports, so copy both and recovery review also hashes them; confirm an existing recovery review again after upgrading. The service-only `refresh-worker.mts` is not a project scaffold or recovery file. Current dependency analysis is separate from execution manifests (`node .sandcastle/dispatch.mts --refresh-only --base <branch>` reassesses every card of a project without admitting or launching anything; add `--ticket <iid>` for one card), shares the dispatch analysis budget and reports pending/stale/error states at every run stage. Do not delete closed or deselected parked cards; selection belongs in their assessment. The board hides a queued card once a successful refresh records `selected: false` (#125), but keeps its record; reselecting the ticket and refreshing shows it again. A failed refresh never hides a card, and other stages are always shown. Refresh never writes the tracker, changes admission or starts/retries work. When testing the refresh path, stub both the `pi` executable and `FACTORY_PI_SUBSCRIPTION_EXTENSION`; production validates extension-file existence before invoking `pi`. The refresh fixtures supply a sentinel file and isolated HOME, so verification needs no provider installation or login.

Factory verification always needs Playwright and headless Chromium, even for static or Node-only projects. Web and CMS layers are optional by stack. If the image lacks browser provisioning, explain that verification refuses to start and ask before changing the Dockerfile. Run the browser layer as root before returning to the agent user; use version 1.65.1 by default, or align with the project's locked playwright-core version without silently changing its pin. Keep `/opt/ms-playwright` readable/executable by the agent. The shared preflight resolves global Playwright with CommonJS via `npm root -g` and launches Chromium as the non-root agent without downloads. See `orchestrator/ADAPTING.md` for explicit rebuild, workflow upgrade and smoke-check steps.

### Docker setup (if chosen)
1. Add the chosen `*.Dockerfile.snippet` files after the glab one, in order: web, CMS, ddev shim, Playwright. Copy `runtime-web/start-web.sh` (and `compat-ddev/ddev-shim.sh` with the shim) into `.sandcastle/` (the snippets COPY them; they must be in the build context).
2. Web layer hook: `start-web.sh <detected docroot>` run as root once the sandbox is ready. With a TOML workflow, remove `setup = []` and add `[[sandbox.setup]]` with `command = 'start-web.sh <docroot>'` and `sudo = true` (optional `timeout_ms`; omitted preserves sandbox default). Legacy-only: `CONFIG.sandboxSetup` in `main.mts`; without it, add `hooks: { sandbox: { onSandboxReady: [{ command: "start-web.sh <docroot>", sudo: true }] } }` to the init template's `main.mts`. Project code reaches Playwright's global install via `NODE_PATH=$(npm root -g)` (ESM ignores it; use CJS or install `playwright` in the project).
3. Verify: build the image (`npx sandcastle docker build-image`); a `maxIterations: 1` run on a throwaway ticket where the agent starts the web layer, loads the page with Playwright, and closes the ticket.
4.
