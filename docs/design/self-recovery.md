# Self-recovery slice

The agreed scope and all ten follow-up decisions are recorded in the [slice 4 plan](../slice-4/plan.md). Use that plan as the source of truth when preparing Factory implementation tickets. High-level requirements are summarized in the [CLI requirements and roadmap](../factory-cli.md#slice-four-self-recovery-requirements).

The retained [repair-agent prompt draft](self-recovery-prompt.md) is design input only. It is not an installed workflow asset or an available recovery feature.

The durable recovery state (episodes, confirmation, attempt budgets, history, and the per-ticket baselines that decide when a human requirement change or verified delivery progress renews a budget) is implemented as a store only; see [Slice four: recovery state](../factory-cli.md#slice-four-recovery-state). The atomic claim a repair attempt will take (shared capacity, the ticket and the project's recovery slot together) is described under [Slice four: launch admission](../factory-cli.md#slice-four-launch-admission). Which branch and worktree an attempt may continue, and the ambiguous cases it refuses, are under [Slice four: resuming recorded work](../factory-cli.md#slice-four-resuming-recorded-work). The independent verification and normal delivery a repaired branch must pass are the ones every run uses; see [Slice four: shared verification and delivery](../factory-cli.md#slice-four-shared-verification-and-delivery).

The premature direct implementation and tests were discarded. Implementation must run through prepared Factory tickets under [AGENTS.md](../../AGENTS.md); this documentation does not queue or dispatch them.
