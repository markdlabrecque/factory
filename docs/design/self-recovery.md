# Self-recovery slice

The agreed scope and all ten follow-up decisions are recorded in the [slice 4 plan](../slice-4/plan.md). Use that plan as the source of truth when preparing Factory implementation tickets. High-level requirements are summarized in the [CLI requirements and roadmap](../factory-cli.md#slice-four-self-recovery-requirements).

The repair-agent prompt is now `orchestrator/prompt.recover.md`, used by `main.mts --recover`; the [original draft](self-recovery-prompt.md) is kept as design history. `factory init` copies the prompt (#63). Jam confirmation (#61, [Slice four: jam confirmation](../factory-cli.md#slice-four-jam-confirmation)) runs after every completed scheduled pass and launches a repair only in a project whose complete recovery workflow is unchanged since a recorded review ([Slice four: reviewed recovery workflow](../factory-cli.md#slice-four-reviewed-recovery-workflow)): a new scaffold, or an existing project upgraded by hand and confirmed with `factory recovery review --confirm`. What it records is shown and reset with `factory recovery status|reset` ([Slice four: recovery status and reset](../factory-cli.md#slice-four-recovery-status-and-reset), #62).

The durable recovery state (episodes, confirmation, attempt budgets, history, and the per-ticket baselines that decide when a human requirement change or verified delivery progress renews a budget) is implemented as a store only; see [Slice four: recovery state](../factory-cli.md#slice-four-recovery-state). The atomic claim a repair attempt will take (shared capacity, the ticket and the project's recovery slot together) is described under [Slice four: launch admission](../factory-cli.md#slice-four-launch-admission). Which branch and worktree an attempt may continue, and the ambiguous cases it refuses, are under [Slice four: resuming recorded work](../factory-cli.md#slice-four-resuming-recorded-work). The independent verification and normal delivery a repaired branch must pass are the ones every run uses; see [Slice four: shared verification and delivery](../factory-cli.md#slice-four-shared-verification-and-delivery). How one attempt is launched, bounded, cancelled and settled is under [Slice four: bounded repair attempts](../factory-cli.md#slice-four-bounded-repair-attempts); what the original #60 acceptance maps to, and what is still missing, is in [recovery-60-verification.md](../recovery-60-verification.md).

The premature direct implementation and tests were discarded. Implementation must run through prepared Factory tickets under [AGENTS.md](../../AGENTS.md); this documentation does not queue or dispatch them.
