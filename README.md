## GitHub tooling

Interactive agents use `gh-axi` for ordinary GitHub operations and plain `gh --attach` for screenshot/video uploads, including the comment that contains them. Factory's runtime continues to use plain `gh` for all GitHub operations.

Factory posts verification screenshots and recordings as native attachments in one issue comment, with Before and After sections and standalone video references for inline playback. This applies to normal and recovery runs and to PASS, FAIL and INCONCLUSIVE verdicts. `--no-push` suppresses implementation-branch pushes, not verification comments. The verifier guard, PASS gate and delivery/CI checks still apply.

The host needs GitHub CLI 2.99.0 or newer with `gh issue comment --attach`, an authenticated account with repository push access, and a supported GitHub.com or Enterprise Cloud host. GitHub Enterprise Server does not support this upload flow. GitHub limits each command to 50 attachments. Keep PNGs below 10 MB and videos below 10 MB for free repositories, or 100 MB where the plan and uploader permissions permit it. MP4 with H.264 is recommended; WebM remains supported. See [media upload research and live verification](docs/research/github-media-uploads.md) for token, privacy and media details.

An unsupported CLI or failed upload stops the run before implementation push or delivery and retains local evidence at the path in the error. Fix the CLI, permissions or media and explicitly retry. A partial upload may leave unreferenced assets; Factory does not fall back to pushing an evidence branch. Existing `sandcastle-evidence` files and historical links remain untouched. GitLab retains its upload-then-comment behavior. These changes ship in new scaffolds; running or customized project copies are not automatically refreshed.

> **Experimental:** [Interactive agents under herdr-core](docs/research/interactive-agents-herdr-core.md) (spike #6) tested attaching to and steering a running agent. It is research only and not supported by Factory.

The Board uses the approved functional tracker design. Each active, blocked or queued ticket has a row of stage dots with a centered line through the current stage. The current dot is solid green when working and red when blocked, stopped or quiet for 20+ minutes, with a soft halo and outward sonar pulse. Reduced motion hides the pulse; background tabs pause it. Real stages remain visible: Queue, Setup, Build, Verify, Post, Push, CI and Shipped. Queued tickets show their recorded blockers, with "Docket is full" only when capacity is the only recorded blocker. The live writer's note is the fallback for older queue records.

Unfinished and stopped tickets stay above the single collapsible **Shipped** section. It starts collapsed and shows the ten latest completions for the current project/status view, newest first. Filtering happens before the limit. Summary and filter counts remain Board-wide; the Shipped section count is the displayed total. Select a ticket title, blank card area or View stats to see stage time, total elapsed, running/queued/blocked time, blocker episodes and bounces. Closing stats returns focus to the invoking button, or to the ticket title for a blank-card click; removed or hidden controls fall back to the Shipped summary. `board.mts` records stage visits on transitions and parked-reason changes, not heartbeats. History is bounded to 1,000 visits per ticket. Older or truncated history is marked incomplete; missing full totals say Unavailable rather than zero. Newer blocked/stopped records retain the last known stage; older ones explicitly say the stage is unavailable.

Run cards retain branch, timing, note, verdict and ticket/PR/evidence links. A card the dispatcher marked done because its work was merged outside Factory (#87) says "Merged outside Factory · PR #N" (GitLab: "MR !N") beside its original verdict, and its Time row shows when the PR merged; hovering the label says which rule matched and that Factory did not verify it again (#88). Working runs also show the latest agent-log line (`.sandcastle/logs/<branch>-*.log`), read on each poll; parked and finished runs show none. Every status has a text label. The Appearance button picks Light, Dark or System, saved in your browser; System follows your OS setting live. Copy `board.mts`, its `admission.mts` and `assessment.mts` imports, and `board.template.html` together to update a project's writer and page. The source change does not install files or restart services.

The HTTP board does not reload. It polls `GET /api/runs` (read-only JSON, the same data as the page) every 10s, pauses in background tabs, and patches cards by run key: new runs fade in, moved runs slide, stage changes get a short highlight and counts slide to the new value. Focus, scroll and filters survive updates. If a poll fails, the board keeps the last good data and says Offline until the next poll works.

A slim strip under the navigation shows when the scheduler's `factory-tick` timer next runs, with a countdown that updates every second: "Next run in 4m 12s". The macOS supervisor agent counts as that timer. The strip says "Running now" while a tick is active, "Scheduler off" when the timer is disabled or stopped, "No timer" when it isn't installed and "Unknown" when the service manager can't be read or the board can't be reached. If the manager ever reports more than one `factory-tick` timer, each gets its own entry. The strip polls `GET /api/timers` (read-only JSON) every 10s. Service-manager queries run asynchronously with timeouts, so an unresponsive manager does not freeze other Board requests. It leaves out legacy `sandcastle-dispatch@` timers, last-run times, tick history and pass timings, and it has no on/off control; use `factory schedule on|off`. Local `board.html` snapshots and evidence pages don't show it. On Linux the next run comes from `systemctl --user list-timers`; on macOS the supervisor saves it to `<state>/scheduler/next-tick.json`. A board installed by `board/install-service.sh` or `install-launchd.sh` has no `cli/` beside it, so its strip is hidden; install through `factory install` for the countdown. Navigating between board and evidence uses a short cross-page transition in browsers that support it. With reduced motion turned on, all of this happens without animation.

Evidence opens in the same tab with image, video and text previews, a Back to board link, and normal browser Back/Forward navigation. Evidence pages never poll, so videos are not interrupted. Text previews stop at 64 KiB; Open original serves the full file.

Without the service, the board assumes it runs from a repo root containing `.sandcastle/` and writes `.sandcastle/board.html`, a static snapshot marked "Snapshot": refresh the file to see newer data. Its evidence links open local folders rather than the HTTP preview pages.

Each card shows a separate **Current ticket** block (#78) with tracker facts, selection, freshness and errors. Closed, excluded and no-longer-selected queued/waiting cards keep their records and stage history but cannot launch. Once a successful refresh confirms that a queued card is no longer selected, the card leaves the board and its queue counts (#125). Selection requires a complete ready list (#135). GitLab reads every page. GitHub Search is capped at 1,000 results even with a larger `--limit`, so a result of 1,000 fails the read and preserves last-good facts instead of implying deselection. Narrow the dispatch filters before retrying such a GitHub refresh. Its run record, history and evidence stay, so later refreshes still check it; restore the label (or whatever selects it) and the next successful refresh brings the card back, and normal dispatch can queue it again. A failed refresh never removes a card, and waiting, running and finished cards stay visible whatever their selection. Cards without an assessment show `Current ticket: not checked yet`, including legacy cards and cards beyond a pass's check limit. This is distinct from a pending refresh, pending analysis or failed check. A failed refresh keeps the last good facts. Requirements, human comments, parent context and dependency definitions invalidate the assessment's own analysis, even for stopped, active and completed cards. **Pending analysis** is distinct from a queued refresh request. Dependency conclusions stay stale until read-only analysis completes. Unknown providers, human-only blockers and tracker errors cannot support a cleared-blocker claim. A stopped ticket whose blockers are confirmed satisfied needs an explicit `factory retry`; this does not change a historical FAIL.

Each non-dry dispatch pass checks up to 25 cards and shares `GRAPH.maxAnalysesPerPass` between execution and assessment analysis. Assessment analysis uses `analyze.mts`'s read-only tools and timeout but never overwrites an execution manifest or changes launch decisions. Assessment-store failures are logged, not admission gates; the board still renders without assessments. Results live in `<state>/assessment/`, with immutable refresh request generations in `<state>/refresh/`. Each card also has an assessment attempt token, allocated before tracker reads. A short per-card cross-process lock protects token allocation and publication, including pending and failure states. Older scheduled or manual attempts cannot overwrite a newer attempt's result or consume its requests. Tracker reads and analysis run outside this lock; it never takes admission locks. Dead lock owners are detected by process identity, not age. A busy, unreadable or abandoned reclamation guard logs a store error instead of blocking dispatch indefinitely. Runs, branches, claims, logs, evidence, corrections and archive state are untouched.

Manual comments, verdict corrections and archive state live in a separate ticket journal (`board/journal.mts`, #98), in `<state>/journal/<project>--<iid>.json`, never in run records, so a run's own verdict, logs and evidence are never rewritten. Events are only appended, under a per-ticket lock, and keyed by tracker project and ticket. The effective verdict is the latest correction for the card's current run, else the run's own verdict; archive state also applies to that run only, so a new execution starts with neither. Each comment or correction tracks its tracker delivery: one poster at a time, and a post that may have reached the tracker is marked for a marker search before any retry. `factory ticket comment` (#99, below) writes comments and `factory ticket sync` (#100) delivers what a failed post left behind; `ticket verdict`, `archive`, `archived`, `show` and `restore` are available too. Shipped cards have an X button named "Archive ticket" (#103). Its tooltip explains that run data, logs and evidence are preserved. A card disappears only after a successful archive; failures stay visible on the card. Snapshot files hide the action. Manually corrected verdicts say "corrected" and retain the original verdict in a tooltip.

The HTTP **Refresh ticket** action requires `POST /api/refresh/<run-key>` and `x-factory-refresh: 1`. It works with scheduling off: the board runs the project's `dispatch.mts --refresh-only --ticket <iid> --base <branch>` in a short-lived process group, bounded to two minutes. One worker per card runs in the server; a click during a check remains pending for a following check. The worker kills surviving members of its own process group after success, failed leader exit, spawn error or timeout, even when descendants redirect their stdio. Unrelated detached groups survive. Its dispatcher child inherits the worker's assessment token so a timeout can record an error, but cannot overwrite a newer scheduled/manual result. The worker finds the checkout through Factory's project registry, the last assessment's project root or its working directory. Missing/ambiguous roots, old dispatcher copies and timeouts record a failure rather than leaving the request pending. Without `--ticket`, `dispatch.mts --refresh-only [--base <branch>]` reassesses every card of that project the same way (up to 25 per run, oldest assessment first, sharing the per-pass analysis budget), so a project that is not opted into scheduling can be kept current. This mode exits before tracker writes, run updates, admission locks or launches. There is no new timer or webhook service. A closed tracker issue proves nothing about a merge or PASS.

Upgrade project copies by hand with `dispatch.mts`, `refresh.mts`, `analyze.mts`, `admission.mts`, `assessment.mts`, `board.mts` and `board.template.html` together. The installed board also needs `refresh-worker.mts` beside `board-server.mts`, `assessment.mts`, `admission.mts`, `board.mts` and the template. Both standalone installers, `board/install-service.sh` and `board/install-launchd.sh`, copy all six board files on install and update. The CLI installer copies the entire board directory. No automatic scaffold upgrade is performed.

Run the board regression tests with `node --test board/*.test.mts`. The installer tests use temporary HOMEs and strict service-manager stubs, then import and serve the copied board without repository-relative files.

## Project configuration

New projects receive a commented **`.sandcastle/factory.toml`**. Configure tracker,
agent/approved model aliases, AND selection filters, work units, dispatch limits,
merge policy, labels, graph, CI and sandbox startup steps there—not in Factory code.
When present it is authoritative with documented defaults and no per-field fallback.
Without it, legacy config/SELECT/CONFIG behavior is preserved. Invalid TOML fails
before credentials, Docker/npm, tracker mutations or launch. Credentials, prompts,
script bodies and machine registry/scheduler files stay separate.

See [the complete schema, profiles and manual migration mapping](docs/project-config.md).
`factory init` repairs legacy scaffolds without creating TOML; `factory update`
never creates or overwrites it. Existing customized workflow code needs a reviewed
upgrade with all runtime/parser helpers; adding TOML alone is not a migration.
The offline parser is pinned smol-toml 1.9.1 (BSD-3-Clause), shipped with the app and scaffold.
Its generated JS stays byte-identical to upstream, with a scoped trailing-space check exemption.

```sh
factory selection explain 137 --project my-project --json
```

Explain is read-only: effective selection/work/dispatch values with explicit/default
sources, eligibility and reliable reasons, separate historical execution holds with
missing/stale facts marked unknown. It starts no work or analysis and writes no state.
Exit 0: evaluated eligible or excluded; exit 1: invalid config, failed read or unknown.
JSON fields: `source`, `settings`, `eligibility`, `reasons`, `executionHolds`.
Legacy customized SELECT cannot be safely inferred and reports unsupported/unknown.

Concurrency still counts active runs across the **shared board** using atomic launch
reservations. `--max` and `--whole-issues` retain their override behavior and report
sources; unsafe integer caps are rejected before the CLI starts shell preflight.
Manual-start exceptions are unchanged. Selection is distinct from capacity,
conflicts, model-resolution requirements and other execution holds.

## Automatic merging

Set `[merge] auto = true` in `.sandcastle/factory.toml` (legacy: `MERGE.auto` in `config.mts`) to opt in. `MERGE.auto: true` supports GitHub and GitLab; `false` keeps manual merging. The optional `MERGE.requiredChecks: ["test", "build"]` lists exact check or job names that must be present and passed, not skipped. An empty or omitted list keeps the all-checks gate.

GitLab opens the MR first, waits for its head pipeline and jobs on the pushed SHA, then requests a SHA-guarded API merge. GitHub also guards the pushed SHA. Missing, pending or otherwise unmet gates leave the PR/MR open, comment the reason and put the run in `waiting` for a person. GitHub failed or cancelled CI retains its existing draft-and-fail behaviour. GitLab uses the project's merge strategy, with `MERGE.method: "squash"` requesting squash. No label or approval gate is added by Factory; tracker-side restrictions still apply. See [the CI gate](orchestrator/ADAPTING.md#two-reference-configs) for setup and upgrade details.

To update later, `git pull` in the checkout and run `factory install` from inside it (or `node cli/bin/factory.mts install`): install prints `Installing from <checkout>` and copies the checkout it was run from. The installed `factory` command run outside any Factory checkout refuses instead of reinstalling its own copy. Add `~/.local/bin` to your PATH if the installer asks. The default install copies the runtime into `~/.local/share/factory/app`; `install --link` uses this checkout instead. The manifest in `~/.local/share/factory/manifest.json` records the app, command and board service. Reinstall refreshes owned files without duplicating entries and refuses to overwrite unowned paths. Config and run history survive uninstall; `--purge` also removes those folders and Docker images labelled `factory.managed=true`.

Set `SANDCASTLE_STATE_DIR=$HOME/.local/state/factory` when running the existing orchestrator or dispatcher to report there. Updates still use the existing scripts; projects, dispatching and scheduling have their own commands (below). Legacy Sandcastle services are detected but never adopted or stopped. Stop an existing board yourself before installing if it occupies port 4444.

### Projects: `factory project` and `factory init`

```sh
factory project add [path]      # record a Git checkout; writes nothing into it
factory project ls [--json]     # registered projects, flagging missing checkouts and missing scaffolds
factory project rm [path]       # forget a project; never deletes files (a deleted checkout: pass its recorded absolute path)
factory init [path] --profile personal --repo owner/repo --image sandcastle-myproject
factory init [path] --profile client --repo group/sub/project --image sandcastle-client --host git.example.com --project-id 42
```

The registry is `~/.config/factory/projects.json` (`{version:1, projects:[{name,root,schedule?}]}`), keyed by the canonical checkout root, written atomically under a lock. `init` adds only the **missing** minimal workflow files to `.sandcastle/` (orchestrator, dispatcher, ticket graph, board module, neutral prompts, `.env.example`, empty `.env` mode 0600, `.gitignore`, and `factory-dispatch.sh`, which runs `dispatch.sh` against Factory's shared state folder), never overwrites, lists what it skipped, and registers the project only after every write succeeded. Existing files are never overwritten. New projects use `factory.toml`; an existing workflow without it stays legacy, with manual migration guidance. When TOML exists it—not stale legacy settings—is authoritative; flags configure new files only. Rerun to repair a partial scaffold. It does not install packages, build images, contact a tracker or provision an environment: Docker, CMS, web-runtime, ddev and Playwright layers remain in the `sandcastle-setup` skill. `.sandcastle` stays the folder name; a move to `.factory` is a later slice. `factory uninstall` lists each registered project's `.sandcastle` with a removal command it never runs.

Scheduling (slice four, in progress) keeps global and project state in different places. The service manager owns the global state: scheduling is on when `factory-tick.timer` is enabled and active (Linux), or when the `com.factory.tick` launch agent is enabled and running (macOS), and Factory stores no on/off flag of its own. Each project's opt-in is the `schedule: {enabled, branch, since}` field of its registry entry. A newly added (or removed and re-added) project is not scheduled. Opting a project in saves the branch its checkout has at that moment and refuses a detached HEAD, a branch that `origin` does not have (as of your last fetch; Factory does not contact the remote), and a `dispatch.sh` that is missing or not executable. Scheduled passes use only that branch and never switch branches, so a checkout on another branch is skipped with the reason. Switching a project off keeps the saved branch; switching it on again saves the branch checked out then. `factory project ls` shows `[scheduled: <branch>]` or `[schedule paused]`. `~/.config/factory/schedule.json` (`{version:1, path, node}`, mode 0600) holds only the PATH and Node that scheduled passes use. A `scheduler.json` left by earlier builds is ignored.

### On a schedule: `factory schedule` (Linux and macOS)

```sh
factory schedule on --project <name|path>   # opt a project in; saves its checked-out branch
factory schedule on                         # install the units, then enable and start the timer
factory schedule status [--project <name|path>] [--json]   # the timer, the tick, and why each project would or would not get a pass
factory schedule off --project <name|path>  # pause one project
factory schedule off                        # disable and stop the timer, then cancel the active tick
journalctl --user -u factory-tick           # the tick log: each pass's start, end, duration and exit code, and every skip with its reason
```

Without `--project` a command is for the global scheduler, even inside a checkout. The bullets below describe Linux (systemd); the macOS bullet says what differs there.

- **One scheduler per user.** `factory schedule on` (after `factory install`) saves your PATH and Node, writes `factory-tick.service` and `factory-tick.timer` in `~/.config/systemd/user/`, records each in the manifest as it is written, then runs `systemctl --user enable --now factory-tick.timer`. The first tick comes about a minute later, then one 5 minutes after each tick finishes, so ticks never overlap. Missed ticks are not replayed, and a failed tick does not stop the timer. If writing or enabling fails, the ledger stays, the error is shown with what systemd reports now, and running `schedule on` again retries. The units get no shell profile, so rerun `schedule on` after moving tools. Run `loginctl enable-linger $USER` so it keeps running when you are logged out (`factory doctor` warns otherwise).
- **A tick** (`factory tick`, internal, run by the service) asks systemd whether the timer is enabled and active before taking its lock, after taking it and before every project; anything else, including a query that fails, means no work. It then visits the registered projects one after another, starting each tick with the next opted-in, unpaused project in turn (saved as `nextRoot`, and advanced before any pass so a failing or cancelled tick still passes the turn on), and runs one dispatcher pass (`.sandcastle/dispatch.sh`, with no `--max` override, with `FACTORY_SCHEDULED=1`, your saved PATH and `SANDCASTLE_STATE_DIR` set to Factory's state folder) for each project that is opted in, not paused, present, on its saved branch and has a current dispatcher copy. A registered project that was never opted in gets a read-only refresh of its cards instead (`node .sandcastle/dispatch.mts --refresh-only --base <the branch it has checked out>`, with the saved Node and PATH and Factory's state folder, as its own process group, cancelled like a pass), so its board stays current without scheduling it; one with a detached HEAD or no `.sandcastle/dispatch.mts` is skipped, and a paused project gets nothing. A refresh takes no turn, is not pass history, and a failed one is logged and recorded on the project (`skipped`, with the refresh result in the reason) without failing the tick. The others are logged with the reason. Each pass runs as the leader of its own process group. The tick exits 1 when a pass fails and 143 when cancelled. There is no pass timeout. Admission uses the cap from the project's dispatcher config, `SELECT.maxConcurrent` in `.sandcastle/dispatch.mts`, counted across every project from the shared board, including launches whose run has not started yet; manual starts (`factory run`, `factory dispatch`) stay overrides. A tick started by hand from a terminal keeps that terminal as stdin; the service has none. `<state>/scheduler/state.json` records the current and last tick and each project's last attempt (`running`, `ok`, `error`, `skipped`, `interrupted`, with the pass pid). `<state>/scheduler/history.json` keeps the timing of the last 1000 passes and ticks (start, end, duration, result, and `interrupted` for a cancelled or dead one), oldest dropped first; it informs any future timeout choice and is never a switch or a timeout itself.
- **Off cancels.** `factory schedule off` runs `systemctl --user disable --now factory-tick.timer`, then `stop factory-tick.service`, then confirms the active tick and its dispatcher pass group are gone. The pass, and the shell, `npx` and ticket-analysis processes under it, get SIGTERM; no later project starts, and the pass is recorded `interrupted`. Ticket runs the dispatcher already launched are detached into their own groups and keep going, and so do their capacity reservations. `off` reports what it saw: that a running tick was stopped and which project's pass was cancelled (a pass that had already finished on its own is named as finished), that none was running, or that it could not read systemd first. Cancellation has its own deadline, never a pass timeout: the owned group gets 30 seconds after SIGTERM, then SIGKILL (that group only), then 5 seconds to disappear. If a pass exits but leaves non-detached children in its group, the tick terminates that group the same way (and records why) before it lets go of it. If anything cannot be confirmed gone, `off` fails and keeps the lock and runtime files so a retry still knows what to cancel; a tick killed outright leaves its pass group recorded, and no new pass starts over it.
- **Uninstall and reinstall.** `factory uninstall` stops scheduling the same way and removes a unit file, the app or any ledgered file only after cancellation is confirmed; `--dry-run` signals and changes nothing. Config, history and projects stay (`--purge` removes Factory's config and state folders). `factory install` over an existing install stops scheduling first, refreshes the owned units from the saved PATH and Node, and leaves the timer disabled: resume with `factory schedule on`. Opted-in projects stay opted in and start nothing by themselves. Install's last line says so whenever it stopped the scheduler or any project is opted in, naming the projects waiting for `factory schedule on`.
- **Opt-in needs a current dispatcher copy.** `factory schedule on --project` refuses a project whose `.sandcastle/dispatch.mts` and `board.mts` predate launch reservations, since scheduled passes would undercount the cap. Copy the files in by hand first (see "Updating a project's copy of the workflow"; `factory update --apply` replaces them when they are unedited).
- **Legacy timers.** `sandcastle-dispatch@<name>.timer` from `install-dispatch.sh` would run passes too. `factory schedule on`, `schedule status` and `factory doctor` warn about the enabled ones. `factory legacy status [--json]` lists them with the checkout each one runs and whether Factory has it registered and opted in; it changes nothing. `factory legacy retire` is the explicit way off them: it runs `systemctl --user disable --now` on each enabled legacy timer and then removes that timer's `~/.config/sandcastle/dispatch/<name>.env`, as `install-dispatch.sh --uninstall` does. A legacy pass already running finishes, ticket runs keep going, the template units stay, and Factory's own scheduler is not turned on. A timer it cannot disable keeps its env file and the command exits 1; run it again. No other Factory command touches a legacy unit. To move a machine from them to `factory schedule`, follow the [cutover runbook](docs/scheduler-cutover.md): retire the legacy timers, refresh each project's copy, opt projects in, then arm.
- **macOS.** The same commands, with launchd in place of systemd. launchd has no timer that counts from when the last run finished, so `factory schedule on` installs one launch agent, `~/Library/LaunchAgents/com.factory.tick.plist` (ledgered), which runs a supervisor, `factory supervise` (internal). The supervisor waits a minute, runs a tick, then waits 5 minutes after each tick finishes, so ticks never overlap and missed ones are not replayed. While it waits, it saves when the next tick is due to `<state>/scheduler/next-tick.json`, so the Board can show a countdown; the file is ignored unless that supervisor process is still running. Each tick asks launchd itself, and works only while the agent is enabled and running; the supervisor keeps no on/off file. `on` runs `launchctl enable`, then `bootstrap` (or `kickstart` if it is loaded but stopped); a supervisor already running is left alone, so after changing Node run `off` then `on`. `off` runs `launchctl disable` first, so nothing can start it again, then `launchctl bootout`: the supervisor gets SIGTERM, cancels its dispatcher pass group exactly as on Linux, and exits successfully, so `KeepAlive` (restart after a crash only) leaves it stopped. Detached ticket runs keep going. `schedule status` shows the agent's enablement, whether it is loaded and whether it is running separately. The tick log is `<state>/scheduler/tick.log` (`tail -f ~/.local/state/factory/scheduler/tick.log`). Uninstall and reinstall stop it the same way first; reinstall leaves the label disabled. Log in for it to run: a launch agent runs only in your login session.
- **Health and timings.** `factory status` shows, above the project's runs, whether the scheduler is on, off or `unknown` (with the reason), whether a tick is running, the last tick, and tick timings; then the project's switch and branch, why it would not get a pass (or `ready`), its last pass, and its pass timings (count, last, median, 90th percentile, longest, and how many ended ok, error or interrupted) with its five most recent passes. Problems are listed: an unreadable service manager, a timer (or macOS agent) enabled but not running or running but disabled, a malformed state, history or launch configuration file, and no tick for two intervals while on. `schedule status` shows the same health and per-project timings for every project; both carry it in `--json`. The timings come from `history.json` and are for judging any future timeout; nothing times out.

### Running work: `factory dispatch`, `run`, `retry`, `status` and `logs`

Run and watch a project's work from `factory` instead of calling `.sandcastle/dispatch.sh` by hand. Each command works on one project: the registered checkout you are standing in, or `--project <name>` (a registered name, or a path inside a registered checkout). Any other directory fails and names the registered projects.

```sh
factory dispatch [--dry-run] [--max N] [--whole-issues]   # one dispatcher pass
factory run <ticket>                                       # run one ticket now, in the foreground
factory retry <ticket>                                     # clear a failed run so the next pass picks it up
factory status [--json]                                    # board service, scheduler health and timings, and every run's stage
factory logs [ticket] [-f] [--recovery]                    # a run's log, or a repair's with --recovery (newest without a ticket; -f follows)
factory recovery status|reset [--json (status)]            # self-recovery state, attempts and reports; reset budgets (launches nothing)
factory recovery review [--confirm]                        # list the recovery workflow files; --confirm records them as reviewed (activates recovery)
factory clean [--dry-run] [--json]                         # delete merged, clean Factory branches and their worktrees (local only)
factory ticket comment <ticket> <text>                     # save a comment in the ticket journal, then post it to the tracker
factory ticket sync [ticket]                               # post the journal's undelivered comments and corrections, never twice
factory ticket verdict <ticket> --verdict pass --message "Tests passed after the fix"
factory ticket archive <ticket>                            # hide a completed history card, keeping all run data
factory ticket archived --json                             # list archived tickets in this project
factory ticket show <ticket>                               # original/effective verdict, history and pending posts
factory ticket restore <ticket>                            # return an archived card to the board
```

- **`dispatch`** runs the project's own `.sandcastle/dispatch.sh` from the checkout root with the same flags (`--max` takes a positive whole number), with `SANDCASTLE_STATE_DIR` set to Factory's state folder, `~/.local/state/factory` (yours wins if set), so the pass shows on the board. The checks and run behaviour are the script's; so is the exit code.
- **`run`** calls `.sandcastle/dispatch.sh --issue <ticket>` the same way: the same checks as a pass, then `main.mts --issue <ticket>` in the foreground. Output goes to the terminal and to `.sandcastle/logs/run-<ticket>.log`; the exit code is the run's. A project whose `dispatch.sh` copy is older than `--issue` gets a clear error: copy `orchestrator/dispatch.sh` into its `.sandcastle/` (see "Updating a project's copy of the workflow"; `factory update --dry-run` shows whether it differs).
- **`retry`** deletes the run's record from Factory's state folder, the same as deleting the JSON file by hand, but only when the run is stopped (failed, or its process exited without finishing). A done, running, queued or waiting run, a stopped run that a recovery claim or a live launch claim still protects (or whose claims cannot be read), or a ticket with no record, is refused with the reason. It keeps the ticket's ownership receipt. It deletes no branch, log or evidence: if a `<ticket>-*` branch is left locally or on origin, it says so and how to delete it, because the dispatcher skips a ticket that has one.
- **`status`** shows the board service's state (`active`, `inactive`, `missing`, or `unknown` with the reason when the service manager can't be reached) and URL, then each of the project's runs, oldest first: ticket, stage, time in that stage, title, branch, verdict, PR and note. A run whose process is gone without finishing shows as `stopped`. `--json` prints `{version:1, project:{name,root,tracker}, board:{service,url}, runs:[...]}`.
- **`logs`** prints `.sandcastle/logs/run-<ticket>.log`, or without a ticket the project's most recently written run log. `-f` keeps printing new output (starting over if the file is truncated) until Ctrl-C.
- **`logs --recovery`** prints a repair log, `.sandcastle/logs/recover-<ticket>.log` (every recovery attempt on the ticket appends to it), or the newest one without a ticket.
- **`recovery status`** shows the project's self-recovery: whether its copy can run repairs, the current jam and its confirmation, the running attempt, each ticket's attempts left and last renewal, recent attempts with outcome, reason, repair log and retained report, renewals and ended jams (`--json` too). `status` shows a short summary of the same.
- **`recovery reset`** ends the jam episode and gives every ticket its two attempts back. It refuses while an attempt is running, unsettled or claimed. It launches nothing (the next scheduled passes re-evaluate the project) and leaves branches, worktrees, run records, logs, reports and evidence alone. Use `retry` to clear one failed run.
- **`recovery review`** is the gate for self-recovery (#63). Recovery runs only when the copy has the complete recovery workflow (`main.mts` with `--recover`, `recovery.mts`, `recovery-sandbox.mts`, `handoff.mts`, `ownership.mts`, `admission.mts`, `assessment.mts`, `board.mts`, `prompt.recover.md`, `prompt.verify.md`) and those files are unchanged since a recorded review. `factory init` ships them and records the review for a new scaffold. An existing project is upgraded by hand ([Upgrading an existing project for self-recovery](orchestrator/ADAPTING.md#upgrading-an-existing-project-for-self-recovery)). Without `--confirm` it lists each file as missing, the same as Factory's copy, different or project-specific, and whether it changed since the last review. `--confirm` records the files as they are now; it refuses an incomplete copy and launches nothing. Any later edit makes recovery inactive until you review again.
- **`clean`** (#96) deletes the project's local Factory branches whose PR/MR merged (the run record is `done` with `mergedAt`, set by the dispatcher for Factory's own merges and for merges made outside it) and the worktree under `.sandcastle/worktrees/` holding each one. It keeps a branch, and says why, when it has commits that are neither in the base nor on `origin/<branch>` as last fetched, when it is checked out in the project's own checkout or a worktree Factory does not own, or when its worktree has uncommitted or untracked changes. The worktree goes first (`git worktree remove`, never forced), then the branch, only at the tip it checked. It works offline (no fetch), never touches a remote branch, and leaves run records, evidence and logs alone. `--dry-run` deletes nothing; `--json` prints `{project, root, dryRun, removed, kept, failed}`. It exits 1 only when Git refused a removal. The scheduler also runs it (#97) after each completed scheduled pass of an opted-in project and logs what it removed or kept to the tick's journal; a failed or cancelled pass, or a project that only gets a read-only refresh, is not cleaned, and a failed clean never fails the tick.
- **`ticket comment`** (#99) saves the comment in the ticket journal (`<state>/journal/`) before anything else, tied to the ticket's current run when it has a record, so a tracker outage never loses it. Then it posts the text, followed by a hidden `<!-- factory-journal:<id> -->` marker, as a comment on the ticket through the project's own tracker CLI on the host (`gh api` for `TRACKER.kind: "github"`, else `glab api` on `gitlabHost`), with that CLI's login. A posted comment records the tracker's comment id. If the CLI is missing, the comment stays pending; if it ran and failed, the comment is marked uncertain, because it may have posted, so `ticket sync` looks for the marker before posting again. Exit 0 when posted, 1 when saved but not posted. Quote the text, or put it after `--` if it starts with `-`.
- **`ticket verdict`** requires `--verdict pass|fail` and a non-empty `--message`. It saves one correction event, preserving the original verdict, and posts one tracker comment naming the previous effective verdict, new verdict and run as a manual correction. Delivery failures leave the correction effective locally and exit 1 with sync pending. It never reruns verification or changes execution stage.
- **`ticket archive|restore`** are idempotent local operations. Only `done` cards in the board's history group without a live admission claim can be archived. Queued, waiting, stopped and active cards are refused. Archive hides the card and its visible counts only, leaving dispatcher records, logs, evidence and tracker issue state untouched. `ticket archived [--json]` lists archived cards; `ticket show <ticket> [--json]` includes the original/effective verdict, comments, full event history and pending/error delivery state even while archived. A new normal admission has a distinct execution identity and inherits neither archive nor corrected verdict. All commands accept `--project <name|path>`.
- **`ticket sync [ticket]`** (#100) delivers every comment and verdict correction still undelivered in the project's ticket journals (or one ticket's). Anything that may already have reached the tracker (a post marked uncertain, or a poster that died mid-post) is first looked for by its hidden marker in the ticket's comments (`gh api --paginate` / `glab api --paginate`); if found, the journal records that comment and nothing is posted again, and if the search fails nothing is posted. Pending items are posted directly. Exit 0 when nothing is left undelivered, 1 otherwise; run it again later.
- **Scheduled recovery across restart and failure** (#64). A running repair is detached: it outlives the tick that started it and `factory schedule off`, and keeps its claim. A repair that crashes is settled by a later tick only once docker confirms its exact container gone; until then the project stays held. Two attempts per jam, then nothing until verified progress, a person's change or `recovery reset`. See [Slice four: scheduled recovery across restart and failure](docs/factory-cli.md#slice-four-scheduled-recovery-across-restart-and-failure).

The project needs `.sandcastle/factory.toml` (or legacy `config.mts`); `tracker.project` (legacy `TRACKER.project`) is the name its run records carry. Not yet: journal output in `logs` (`logs` reads no journalctl; the scheduler's log is `journalctl --user -u factory-tick`, on macOS `<state>/scheduler/tick.log`, a legacy dispatcher timer's `journalctl --user -u sandcastle-dispatch@<name>`), running every registered project in one command, and refreshing `.sandcastle` copies. The [CLI plan](docs/factory-cli.md#roadmap) tracks the remaining slices. `.sandcastle` stays the folder name; migration to `.factory` is deferred to a future slice.

## Running the dispatcher

From the project, with the integration branch checked out:

```sh
.sandcastle/dispatch.sh --dry-run   # show what would start, launch nothing
.sandcastle/dispatch.sh             # one real pass
.sandcastle/dispatch.sh --issue 42  # run ticket 42 now, in the foreground
```

It uses the checked-out branch as the base (it must be on origin), checks that `node`, Docker and the tracker and agent CLIs (`glab` and `claude`, or `gh` and `pi`) are there and logged in, and that the image in `CONFIG.image` exists and was built for your user. From a terminal it builds a missing or mismatched image; under the timer it stops and prints the build command instead. Other arguments go to `dispatch.mts`: `--max N` (concurrent runs across every project sharing the state folder, default 3, counting launches whose run has not started yet) and `--whole-issues` (one run per issue, ignoring Tasks). With the Factory CLI, `factory dispatch [--dry-run]` and `factory run 42` do the same from anywhere in a registered project (see "Running work" above).

See every run's stage with `factory status` and a run's log with `factory logs <iid> [-f]`. Retry a failed run with `factory retry <iid>`, or by deleting its record, `<state dir>/<project>--<iid>.json`. The next pass picks the ticket up again. The `factory` commands, `factory-dispatch.sh`, plain `dispatch.sh` and the dispatcher timer all use Factory's state folder, `~/.local/state/factory`, unless `SANDCASTLE_STATE_DIR` is set.

### On a schedule (Linux)

With the Factory CLI, use `factory schedule` instead (see "On a schedule: `factory schedule`" above), and move over with the [cutover runbook](docs/scheduler-cutover.md) so passes don't double up. Without it, each project gets its own systemd user timer, `sandcastle-dispatch@<name>.timer`, which runs a pass 5 minutes after the last one finished. All projects share the run cap and the board; a launched run counts against the cap from the moment it is spawned, before it writes its own record, so passes that follow closely (or another project's) never overfill it. There's no launchd version of these legacy per-project timers; on macOS use `factory schedule`.

```sh
cd ~/Projects/<project>                       # with the integration branch checked out
.sandcastle/dispatch.sh --dry-run             # once from a terminal: builds the image, checks logins
<sandcastle-helper>/orchestrator/install-dispatch.sh            # name = the repo folder's name
<sandcastle-helper>/orchestrator/install-dispatch.sh --name foo # if two repos share a folder name
loginctl enable-linger $USER                  # once per machine: keep timers running when logged out
```

```sh
systemctl --user list-timers 'sandcastle-dispatch@*'   # every project's next pass
journalctl --user -u sandcastle-dispatch@<name> -f     # one project's dispatcher log
<sandcastle-helper>/orchestrator/install-dispatch.sh --uninstall <name>
factory legacy retire                                  # with the Factory CLI: every enabled legacy timer at once
```

The timer never builds the image: after a Dockerfile change, run `.sandcastle/dispatch.sh --dry-run` from a terminal to rebuild it. To change a project's base, check out the other branch in its repo; the next pass uses it.

Upgrading from the single-project timer:

```sh
systemctl --user disable --now sandcastle-dispatch.timer
rm ~/.config/systemd/user/sandcastle-dispatch.{service,timer}
```

then run `install-dispatch.sh` from each project.

### Updating a project's copy of the workflow

Projects run their own copy of the files in `.sandcastle/`, so changes here don't reach them on their own. To see where a copy stands, run `factory update --dry-run` inside the project (or `--project <name|path>`; `--json` for the raw list). It writes nothing and sorts every scaffolded file except `.env`: **missing** (would be created), **outdated** (exactly an earlier Factory version, so unedited; would be replaced), **edited locally** (matches no Factory version; kept, merge by hand), **project-owned** (`factory.toml` always, including when missing; `config.mts`, `main.mts`, `dispatch.sh`, `prompt.md` and `prompt.verify.md` when they differ from Factory's copy, are templated or are missing; never written by update, merge by hand) and **current**. Earlier versions come from the Git history of the Factory checkout it runs from, or, for a copied install, from `scaffold-history.json`, which `factory install` writes into the app from the checkout's history; without either, every differing file counts as edited. To make the changes, pull this repo, reinstall with `factory install`, and run `factory update --apply` in the project (one of `--dry-run` or `--apply` is required). It creates the missing files and replaces the outdated ones, and nothing else; it lists the edited and project-owned files again for you to merge by hand, together with the files you adapted outside the scaffold (`sandbox/bootstrap-site.sh`). A file that changes between the check and the write is left alone. Then review settings in `factory.toml` (legacy: `config.mts`/SELECT/CONFIG) against the documented schema without automatically migrating, and run `.sandcastle/dispatch.sh --dry-run`. Updating the recovery workflow files makes self-recovery inactive until `factory recovery review --confirm`; `--apply` says when that applies but never records a review for you.

### On a new machine

```sh
git clone <project> && cd <project> && git checkout <integration branch>
npm install
cp .sandcastle/.env.example .sandcastle/.env    # then fill it in; it's gitignored
glab auth login --hostname <gitlab host>
claude auth login
.sandcastle/dispatch.sh --dry-run               # builds this machine's image
```

Each machine builds its own image (CPU architecture and user ID differ). Don't run dispatchers for the same project on two machines: each keeps its own state, so they would start the same tickets twice.
