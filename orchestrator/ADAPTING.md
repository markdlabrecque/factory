# Orchestrator

When adapting tests or verification prompts, follow [TESTING.md](../TESTING.md). Verify Factory-owned behavior and the systemd command contract with stubs; missing real systemd alone does not make a verdict INCONCLUSIVE.

For development in this repository, follow [AGENTS.md](../AGENTS.md): prepare tickets and run implementation through Factory. The [slice 4 self-recovery plan](../docs/slice-4/plan.md) records the agreed scope and all follow-up decisions; the [CLI requirements](../docs/factory-cli.md#slice-four-self-recovery-requirements) summarize them. `main.mts --recover <attempt> --attempt-record <file>`, `recovery.mts`, `recovery-sandbox.mts` and `prompt.recover.md` are the repair half of recovery (#60, verified and continued by #74). Since #61 the scheduler's tick triggers them for a jam confirmed on two completed scheduled passes, but only in a project whose copy has the complete recovery workflow and a recorded review of it (#63, `cli/src/recovery-review.mts`). `factory init` copies `prompt.recover.md` and records the review for a new scaffold; an existing project follows [Upgrading an existing project for self-recovery](#upgrading-an-existing-project-for-self-recovery).

> **Experimental, not supported:** attaching to a running agent (herdr-core) was only tested in a spike; see [the report](../docs/research/interactive-agents-herdr-core.md). This workflow still runs its agents non-interactively.


`main.mts` takes one ticket through: branch off an integration branch, implementer run, verifier run (screenshot/video evidence plus a verdict), evidence posted to the ticket, then on PASS push and deliver. The verifier, evidence and delivery steps live in `handoff.mts` (copy it with `main.mts`), shared with slice four's recovery runs so a repaired branch gets the same independent verifier (`AGENT.model`), PASS gate, push and delivery; before verifying, it removes an earlier `verdict.md` and clears the record's verdict and PR, so a stale PASS never counts, and a repaired branch's PR and evidence comment name the recovery attempt. With `--recover <attempt> --attempt-record <file>` (started only by Factory's recovery launcher, after it claimed the ticket and recorded the attempt's UUID and exact container name) `main.mts` checks the attempt record and claimed run record agree, then runs `recovery.mts` `runRecoveryAttempt`: the ticket's recorded worktree in its own container `factory-recovery-<uuid>` from `recovery-sandbox.mts` (not Sandcastle's `createSandbox`; attempt-private Git metadata with only the ticket's branch; only `.sandcastle/evidence/<ticket>/recovery/<uuid>/` writable, earlier evidence copied read-only), the repair agent (`prompt.recover.md`, `AGENT.model`) for exactly 900000 ms after the container is ready and set up, a validated `recovery-report.json`, then the same verifier and delivery with `origin: repaired` on the exact tip, imported into the branch only by compare-and-swap. A timeout or SIGTERM aborts the agent, removes that exact container and confirms it is gone (else the attempt stays `cleanup-pending`), keeping commits, dirty files and evidence; the outcome goes to the host-owned attempt record. Copy `recovery.mts` and `recovery-sandbox.mts` with `main.mts`; both are import-safe. It never closes the ticket; once the work is merged, the next dispatcher pass closes a Task or moves a ticket to `LABELS.done` (see below). Written against `@ai-hero/sandcastle` 0.14.0 with the Docker provider.

## Two reference configs

The code is shared. `config.mts` decides the tracker (`TRACKER.kind`), the agent (`AGENT`) and what happens after the push (`MERGE`).

| | `config.mts`: client and Affinity Bridge work | `config.personal.mts`: personal projects |
| --- | --- | --- |
| Tracker | GitLab via `glab` (`tracker.gitlab.mts`) | GitHub via `gh` (`tracker.github.mts`) |
| Units of work | GitLab Tasks | GitHub sub-issues |
| Agent | Claude Code, `CLAUDE_CODE_OAUTH_TOKEN` in `.sandcastle/.env` | Pi with the `pi-claude-subscription` provider (drives the Claude Code CLI on a subscription): host `claude auth login`, container `CLAUDE_CODE_OAUTH_TOKEN` in `.sandcastle/.env`; no OpenAI login |
| Implementer model | fixed, `AGENT.model` | from the ticket: exactly one of `model:sonnet`, `model:opus` labels, or the ticket isn't started |
| Verifier / analysis model | `AGENT.model` / `GRAPH.model` (`sonnet`) | fixed: `pi-claude-subscription/claude-opus-5-5` / `pi-claude-subscription/claude-sonnet-5-5` |
| After the push | wait for the branch pipeline, open an MR; a person merges | open a PR; merge it once every CI check on the pushed commit passes |
| Evidence images | uploaded to the ticket | committed to the `sandcastle-evidence` branch and linked |

Both adapters offer `mergedPr(iid, branch, base)` (#86) for spotting work merged outside Factory: the newest PR/MR merged into the base from the run's recorded branch, else the newest whose title starts with `#N:` (not `#N0:` or a mention elsewhere). It returns the number, title, URL, merge time and which rule matched. A closed issue alone is never treated as a merge. Copy `tracker.mts`, `tracker.gitlab.mts` and `tracker.github.mts` together.

For a personal project, install `config.personal.mts` as `.sandcastle/config.mts` (`factory init --profile personal` does this). Setup:

1. **Host:** `claude auth login`, and install the provider where Pi discovers it and `preflight.mts` looks: `git clone --depth 1 --branch <tag> https://github.com/markdlabrecque/pi-claude-subscription.git ~/.pi/agent/extensions/pi-claude-subscription && cd ~/.pi/agent/extensions/pi-claude-subscription && npm ci --omit=dev --ignore-scripts` (a release tag; v1.6.0 is the one checked here). `pi install git:…` is not used: it runs the package's husky `prepare` hook, which fails. Host analysis loads it with an explicit `-e <extension>/index.ts` next to `--no-extensions`, so no other extension is enabled; the path defaults to `~/.pi/agent/extensions/pi-claude-subscription/index.ts` (override with `FACTORY_PI_SUBSCRIPTION_EXTENSION`).
2. **Container:** the image needs the Claude Code CLI and the extension: use `layers/agent-pi/pi.Dockerfile.snippet`. Sandcastle's Pi adapter runs `pi -p --mode json --model <provider/id>` in the container, and the extension spawns `claude -p`. Nothing from the host's `~/.claude` or `~/.pi` is copied into the image. The CLI authenticates at run time with `CLAUDE_CODE_OAUTH_TOKEN` from `.sandcastle/.env` (`claude setup-token`), which Sandcastle passes to the container. The extension strips `ANTHROPIC_API_KEY`, so the subscription is what is used.
3. **Preflight:** `dispatch.sh` runs `preflight.mts` (`subscriptionPreflight` in `models.mts`): the extension file exists, `claude auth status` is logged in, and `pi --list-models` shows the configured models from the provider, then checks the container token with an empty Messages request. No value is printed or put on a command line; OpenAI is never consulted.

Only two models are used; `main.mts` and `dispatch.mts` refuse to run if `AGENT.model` or `GRAPH.model` is anything else (`models.mts`). A custom Pi config on `openai/` models still works: `main.mts` mints a per-run `OPENAI_API_KEY` from the host's pi login only for such models.

**Ticket writers:** the runtime model comes from the label (`model:sonnet` or `model:opus`). Put the same full ID in the ticket body (`**Pi model:** …`, `**Model label:** …`) for people, but the body alone schedules nothing and is never parsed.

**The CI gate** (`ci.mts`) is deterministic. Sandcastle merges only when at least one check on the PR's head passed and every other one passed or was skipped, and only while the head is still the commit it pushed (`gh pr merge --match-head-commit`). Failed or cancelled checks, no checks within `CONFIG.noPipelineMinutes`, or checks still running after `CONFIG.ciWaitMinutes` mean no merge: the PR becomes a draft with a comment, and the run stops. So CI must run on every PR, with no `paths` filter. Sandcastle merges in code, so no branch protection or GitHub auto-merge setting is needed.

```
npx tsx .sandcastle/main.mts --base <integration-branch> [--issue N] [--no-push]
```

## Install into a project

`factory init` does this for the files below (except `sandbox/`, and with neutral `prompt.md`/`prompt.verify.md`, an empty `sandboxSetup` and `preflight.mts` added). By hand, copy into the project's `.sandcastle/`: `config.mts` (or `config.personal.mts`, renamed to `config.mts`), `main.mts`, `dispatch.mts`, `dispatch.sh`, `refresh.mts`, `graph.mts`, `analyze.mts`, `tracker.mts`, `tracker.gitlab.mts`, `tracker.github.mts`, `ci.mts`, `models.mts`, `manifests.mts`, `preflight.mts`, `handoff.mts`, `recovery.mts`, `recovery-sandbox.mts`, `ownership.mts`, `prompt.md`, `prompt.verify.md`, `prompt.analyze.md`, `prompt.recover.md`, `sandbox/`, and `board.mts` + `admission.mts` + `assessment.mts` + `board.template.html` from `../board/`. Add `evidence/`, `state/`, `logs/` and `board.html` to `.sandcastle/.gitignore`. The image comes from the `sandcastle-setup` skill (needs the tracker, web runtime, CMS and Playwright layers, plus the Pi layer for the personal config). The host needs Node 22.18+, Docker, and on the PATH and logged in: `glab` and `claude` (client config) or `gh` and `pi` (personal config).

Assessment refresh uses `<state>/assessment/<card>.generation` and a short `<card>.lock`, separate from admission. Allocate an attempt before catalogue, selection or ticket reads. Compare its token under the same lock before publishing pending, success or failure and consuming captured requests. The manual worker passes `FACTORY_REFRESH_KEY` and `FACTORY_REFRESH_ATTEMPT` to its dispatcher child, which reuses that attempt instead of allocating another. Scheduled passes allocate their own attempts, as does `dispatch.mts --refresh-only` without `--ticket`, which reassesses every card of the project (up to `REFRESH_PER_PASS`, oldest assessment first) and exits before tracker writes, run updates or admission; use it to keep a project that is not scheduled current. Keep `refresh.mts`, `assessment.mts` and the installed `refresh-worker.mts` at the same version. Only process-identity helpers come from `admission.mts`; no admission lock or run record is touched. Tracker reads and analysis never hold the assessment lock. Dead-owner reclamation is serialized by `<card>.lock.reap`; a corrupt lock, live owner or abandoned guard fails safely with a logged store error after a bounded wait. Inspect the named process and paths before manually removing an abandoned lock/guard, never remove one by age alone.

The board worker kills only its dispatcher's process group on leader exit, close, spawn error and timeout. This includes children and grandchildren that closed or redirected stdio and would otherwise outlive the leader. It does not kill independently detached ticket runs. The real-process regression tests cover both inherited and redirected stdio for successful, failed and timed-out commands; two-process tests gate an older analyst until the newer manual/scheduled result is published.

Refresh integration tests exercise the real argument validation against a fixture-owned `FACTORY_PI_SUBSCRIPTION_EXTENSION` and a stub `pi` executable. The extension file is a sentinel and is never executed. Do not install a real provider or use a developer's login to make these tests pass in CI.

The always-on board service uses the same `board.template.html` for the board and evidence previews. Keep `board.mts`, `admission.mts`, `assessment.mts`, `refresh-worker.mts`, `board-server.mts` and `board.template.html` together when updating the service. The approved tracker design gives unfinished tickets stage dots and centered connectors through the current stage. Working dots are solid green, while blocked/stopped/quiet dots are red, with soft halos and sonar pulses. One collapsible Shipped section shows the ten latest completions after the current filters apply; stopped runs remain unfinished. Ticket titles and View stats open timing, blocker and bounce details. Closing details returns focus to the invoking button, with a Shipped-summary fallback when that control is removed or hidden. `board.mts` now retains stage visits on transitions and parked-reason changes. Legacy history is explicitly incomplete, and full totals say Unavailable when they cannot be measured. The history limit is 1,000 visits, with truncation marked incomplete. Copy the updated writer as well as the template to collect future stats; historical visits cannot be reconstructed. Queue reasons use structured `queueReasons` when supplied, otherwise the writer's existing note, and suppress secondary capacity without changing admission. An Appearance panel picks light, dark or system mode, saved in browser storage. The service also serves `GET /api/runs` (read-only JSON); the HTTP board polls it every 10s and animates changed runs in place instead of reloading, and respects reduced motion. Its sticky navigation links back to the board; evidence opens in the same tab and never polls, so playback is not interrupted. Text previews are limited to 64 KiB, with originals still available. Local `board.html` is a static snapshot that links to evidence folders instead of preview pages. Cards without an assessment show `Current ticket: not checked yet`, distinct from refresh pending, analysis pending and a failed check. To give an existing project the new board, copy `board.mts`, `admission.mts`, `assessment.mts` and `board.template.html` again (they hold no project config), and reinstall or restart the board service yourself.

`board/board-prototype.html` is a branch-only throwaway design lab with simulated data. The README's "Board design lab" documents its per-ticket dot trackers, vertically centered connectors through the current stage, solid green current dots for healthy states and red dots for bad states with soft halos and outward sonar pulses that freeze on Pause and hide with reduced motion, queue blockers, one collapsible latest-ten Shipped section, ticket stats, demo controls and system/light/dark themes. The prototype replaces Assembly and Megastructure; it was updated directly with human approval, without Factory. It is not copied into projects, not installed by Factory or `factory init`, and remains a preview file even though its approved design now powers `board.template.html`; do not copy it with the board files.

## Upgrading an existing project for self-recovery

Self-recovery (#63) runs only when the project's `.sandcastle` has the complete recovery workflow and a person has reviewed it as it is now. The workflow is `main.mts` (with `--recover` and `--attempt-record`), `recovery.mts`, `recovery-sandbox.mts`, `handoff.mts`, `ownership.mts`, `admission.mts`, `assessment.mts`, `board.mts`, `prompt.recover.md` and `prompt.verify.md`. Factory keeps the review on the host (`~/.local/state/factory/recovery/<key>.review.json`, the SHA-256 of each of those files), never in the project. A missing file, a `main.mts` without `--recover --attempt-record`, no review, or any edit after the review keeps recovery inactive. Jams are then only recorded. `factory status` and `factory recovery status` say why.

A new scaffold from `factory init` gets every workflow file and is recorded as reviewed, so recovery is active. If you edit any of those files later (for example `sandboxSetup` in `main.mts`), review again. `factory init` on a project that already had any of them records nothing. It never changes existing files.

To upgrade an existing project by hand (nothing is merged automatically; `factory update --dry-run` lists which files are missing, outdated, edited locally or project-owned first, and `factory update --apply` copies in the missing and unedited outdated ones for you, leaving step 2 for the edited files and step 3 as it is):

1. Stop scheduled work for the project while you change it (`factory schedule off --project <name>`, or wait until nothing is running).
2. Copy `prompt.recover.md`, `recovery.mts`, `recovery-sandbox.mts`, `handoff.mts` and `ownership.mts` from this folder, and `board.mts`, `admission.mts`, `assessment.mts` and `board.template.html` from `../board/`. Keep `dispatch.mts`, `refresh.mts`, `analyze.mts` and `graph.mts` at the same version.
3. Merge `main.mts` by hand. Take this version's `--recover`/`--attempt-record` mode and imports, and keep your `image`, `sandboxSetup` and other customizations. Keep your project's `prompt.verify.md`; it is the verifier recovery runs too.
4. Check the copy: `.sandcastle/factory-dispatch.sh --dry-run`. Then run `factory recovery review --project <name>`. It lists each file as missing, `same as Factory's`, `differs from Factory's copy` or `project-specific`, and whether it changed since the last review.
5. When you are satisfied, run `factory recovery review --confirm --project <name>`. It refuses an incomplete copy. It records the files as they are, launches nothing and makes recovery active. Turn scheduling back on if you stopped it.

Board dependency-list audit for #78:

- Project copy lists and `cli/src/scaffold.mts` include `assessment.mts` because both `board.mts` and `refresh.mts` import it; `refresh-worker.mts` belongs only in the installed service.
- Both standalone installers copy `admission.mts`, `assessment.mts` and `refresh-worker.mts` because the copied board/server import them. CLI install already copies the whole `board/` directory, so it needs no new file entry.
- `cli/src/recovery-review.mts` includes `assessment.mts` in `WORKFLOW` and `SHIPPED` because the repair path imports `board.mts`; an existing review must be confirmed again after this upgrade. The service-only worker is not part of recovery review.
- Scheduler upgrade advice includes the same mandatory board imports; admission-only imports and tests do not copy a board and need no assessment dependency. Complete-recovery test fixtures include it so they exercise the real review gate.

Since #64 Factory's `admission.mts` treats a claim owner that exited but was never reaped (a zombie) as gone. A copy taken before that shows as `differs from Factory's copy`; take the new one when you next upgrade. Factory's own settle step uses its own copy, so a crashed repair is settled either way.

Factory never applies a repair's host-side workflow follow-up (`requiresHostUpdate`) to this copy or restarts services. Make such changes with this procedure, then review again.

## What is generic

Branching, the two agent runs and the verifier guard (it must not commit, move HEAD or dirty the tree), evidence upload and the ticket comment, the verdict gate, the push/CI/MR step, and the board updates. The container never holds a tracker token; every tracker call runs on the host with its own `glab` or `gh` login.

## What to adapt per project

1. **`config.mts`:** the tracker (GitLab host, project path and id; or GitHub `owner/repo`), the agent and merge settings, the milestone, every label Sandcastle filters on or writes (including `LABELS.done`, the stage a ticket moves to once its work is merged), whether Tasks are the units of work (`SUBTASKS`), and the ticket graph settings. `main.mts` and `dispatch.mts` check at startup that every label exists. From a terminal they offer to create missing ones; declining, or running without a terminal (the timer), quits.
2. **`CONFIG` at the top of `main.mts`:** image name, CI wait times, and `sandboxSetup` (commands that run in the container before the agent starts).
3. **`sandbox/bootstrap-site.sh`:** installs a throwaway site with synthetic data. The shipped version is Drupal from config (mirrors the project's CI e2e job). A WordPress or other stack needs its own; keep the contract that it ends with the site answering on `http://127.0.0.1`.
4. **`prompt.md`, Environment section:** how the site is reached, how to create content, which test commands to run and which not to.
5. **`prompt.verify.md`:** fixture advice and the before/after procedure. The `git checkout` + `drush updb/cim/cr` steps are Drupal specific.
6. **CI behaviour:** GitLab: if branch pushes never get a pipeline, the "no pipeline appeared" fallback is the normal path; if they always do, consider dropping it. GitHub with `MERGE.auto`: CI must run on every PR, or nothing merges.
7. **Integration branch:** `--base` is required. Some projects use a different integration branch per epic.

## Running many tickets: the dispatcher

`dispatch.mts` lists the tickets that qualify and starts one detached `main.mts --issue N` run for each, up to a cap on concurrent runs.

```
.sandcastle/dispatch.sh [--dry-run] [--max N] [--whole-issues]
.sandcastle/dispatch.sh --issue N [--no-push]
```

`dispatch.sh` runs one pass with the defaults: the base is the branch checked out where you run it (it must be on origin). It first checks `node`, the tracker CLI (`glab` or `gh`), the agent CLI (`claude`, or `pi` with the subscription preflight above; a custom `openai/` Pi config checks `pi auth check --provider openai`), `curl` and Docker are there and logged in; that `.sandcastle/.env` exists and its agent credential is accepted (by an empty Anthropic request: `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` for the client config's Claude Code, only `CLAUDE_CODE_OAUTH_TOKEN` for the subscription provider, which strips `ANTHROPIC_API_KEY`; no tokens are used, and no value is printed); and that the `CONFIG.image` image exists and was built for your UID. From a terminal it builds a missing or mismatched image (`npx sandcastle docker build-image --image-name <CONFIG.image>`); without one, as under the timer, it stops and prints that command. It then runs `npm ci` (or `npm install` without a lockfile) when `node_modules/@ai-hero/sandcastle` is missing or older than `package-lock.json`, so a pass never fails on an uninstalled `@ai-hero/sandcastle`. A `factory init` project also has `.sandcastle/factory-dispatch.sh`, which changes to the project root, defaults `SANDCASTLE_STATE_DIR` to Factory's state folder (the caller's value wins) and runs `dispatch.sh` with the same arguments. With the Factory CLI, `factory dispatch [--dry-run] [--max N] [--whole-issues] [--project <name>]` does the same for a registered project (the one you are standing in, or the named one) without `factory-dispatch.sh`: it runs `.sandcastle/dispatch.sh` from the project root against Factory's state folder. `dispatch.sh --issue N` does the same checks, then runs that one ticket now, in the foreground, instead of a pass: `npx tsx .sandcastle/main.mts --base <branch> --issue N`, with any extra arguments (such as `--no-push`) going to `main.mts`; the output also goes to `.sandcastle/logs/run-N.log`, and the exit code is the run's. `--dry-run` and `--max` are refused with `--issue`. `factory run N [--project <name>]` calls it for a registered project, against Factory's state folder; a project with an older `dispatch.sh` (no `--issue`) needs the new copy first. All five slice-three commands (`dispatch`, `run`, `retry`, `status`, `logs`) are described together in the README's ["Running work"](../README.md#running-work-factory-dispatch-run-retry-status-and-logs) section and specified in [the CLI plan](../docs/factory-cli.md#slice-three-spec). Without `--issue`, extra arguments go to `dispatch.mts`, which can also be run directly: `node .sandcastle/dispatch.mts --base <integration-branch> ...`.

- **Which tickets:** milestone and labels are in `config.mts`; the rest (assignee, excluded assignees, author, issue type, confidential, search, order, sort, cap, stagger) is in the `SELECT` block at the top of `dispatch.mts`, each commented with an example.
- **GitLab Tasks.** With `SUBTASKS.enabled` (the default), a ready issue that has Tasks (its "Child items") is a container: each open Task gets its own run, branch and MR, with the parent's description as context. A Task that also carries the ready labels itself is still one run, never two. Ready and exclude labels go on the parent; an exclude label on a Task holds back just that Task. An issue without Tasks is one run, as before. `--whole-issues` (or `enabled: false`) makes every ready issue one run, Tasks or not.
- **Merged work.** Every pass checks the runs whose MR merged into their base: a Task is closed, a whole ticket moves to `LABELS.done` (the ready labels come off; it stays open). A parent moves to `LABELS.done` once every one of its Tasks is closed, however they were closed; it is never closed by Sandcastle.
- **Merged outside Factory (#87).** Every pass also asks `mergedPr` about each `stopped`, `queued` or `waiting` card of the project. When a PR/MR from the run's recorded branch, or one titled `#N: ...`, was merged into the base, the card moves to `done` with the PR (`mr`), the PR's merge time (`mergedAt`) and `mergedOutside` (the PR number and which rule matched); its verdict is kept, nothing is re-verified, and it is not launched. If the ticket is still open, a Task is closed and a whole ticket moves to `LABELS.done`, as for Factory's own merges. The move happens under the admission lock (`markMergedOutside` in `board.mts`), so a card a run or recovery claimed meanwhile is left alone. A closed issue alone never counts. `--dry-run` only logs it. The board labels the card "Merged outside Factory · PR #N" (GitLab: "MR !N") beside the kept verdict, with the merge time in its Time row (#88). Copy `dispatch.mts`, `board.mts` and `board.template.html` together.
- **Cleaning up merged branches (#96).** `factory clean [--dry-run] [--project <name|path>]` deletes a merged ticket's local `<iid>-<slug>` branch (its run record is `done` with `mergedAt`) and its worktree under `.sandcastle/worktrees/`, but only when every commit is in the base or on `origin/<branch>` as last fetched and the worktree is clean; anything else is kept and reported. Remote branches are never touched. The run record stays, so the ticket is still skipped. The scheduler runs the same clean after each completed scheduled pass (#97), so a scheduled project needs no manual cleanup; the tick's log lists what it removed and kept.
- **Ticket journal (#98).** Manual comments, verdict corrections and archive state are kept apart from run records, in `journal/<project>--<iid>.json` in the state dir (`board/journal.mts` in the Factory checkout; not copied into projects). The dispatcher never reads it, so it cannot change which tickets launch, and a new run of a ticket starts with no corrected verdict and no archive. The `factory ticket` commands that write it come later (#99-#102).
- **Skipped tickets:** any ticket with a running or finished run record, or a `<iid>-*` branch. A failed run is not retried automatically; delete its JSON file from the state dir to retry it, or run `factory retry <iid> [--project <name>]`, which deletes it only when the run is stopped and warns if a `<iid>-*` branch would still hold the ticket back. Tickets the ticket graph holds back stay on the board as `queued` with the reason; `factory status [--json] [--project <name>]` lists the same records (stage, time in stage, note) in a terminal, with the board service's state, the scheduler's health and the project's scheduled pass timings.
- **Capacity:** runs in flight are counted from the board, across all projects sharing the state dir. Each launch is on the board (stage `setup`, note `starting`) from the moment the dispatcher spawns it, owned by the new process, so the shared cap of 3 counts it in every later pass, this project's or another's, before the run writes its own record; a launch that exits before it starts is dropped, not marked stopped, so the next pass retries it. The claim is atomic: before each spawn the dispatcher rechecks the cap and the ticket in the admission record (`admission/state.json` in the state dir, under its one lock; `claimRun` in `board.mts`, `admission.mts`), so passes running at the same moment, in any project, cannot overfill the cap or launch one ticket twice. The claim's token goes to the run, which fences its board writes with it, so a stale run never overwrites a newer claim; a project a recovery attempt holds admits nothing until that attempt is settled. `main.mts` also writes an ownership receipt (`ownership/` in the state dir, `ownership.mts`) before it creates the ticket's branch and worktree. Copy `dispatch.mts`, `board.mts`, `admission.mts`, `assessment.mts`, `main.mts` and `ownership.mts` together. Each pass also rechecks the project's existing cards against the tracker (`refreshProject` and `refreshCards`, #78), including parked cards that closed or left selection. Those cards retain their records/history and are not launch candidates. Current dependency analysis has its own freshness key covering requirements, human notes, parent context, catalogue definitions and recorded implementer blockers. Its results live only in `assessment/`, never admission manifests. It shares the remaining `GRAPH.maxAnalysesPerPass` budget after execution analysis and uses the same read-only tools/timeouts. Pending analysis and errors are explicit; unresolved/human-only blockers and failed lookups are unknown, not satisfied. Store errors are logged without gating launches or board rendering. The board's manual action runs the project's `dispatch.mts --refresh-only --ticket <iid> --base <branch>` even with scheduling off. It exits before tracker writes, board updates or admission, and the server bounds its process group to two minutes. Register the project root or run a pass from it first; missing or ambiguous roots record an error. Requests have immutable generations, so finishing an older check cannot erase a newer one. Upgrade `dispatch.mts`, `refresh.mts`, `analyze.mts`, `board.mts`, `admission.mts`, `assessment.mts` and the template together by hand. The installed server additionally needs `refresh-worker.mts`. A refresh never starts or retries ticket work. Manual starts (`factory run`, `dispatch.sh --issue`) are not held to the cap.
- **Logs:** each run writes to `.sandcastle/logs/run-<iid>.log`; `factory logs <iid> [-f]` prints (and follows) it from anywhere in a registered project. A recovery attempt appends to `.sandcastle/logs/recover-<iid>.log`; `factory logs <iid> --recovery` prints it, and `factory recovery status` shows the project's jam, attempts, budgets and retained reports (`factory recovery reset` renews the budgets without launching anything). Add `logs/` to `.sandcastle/.gitignore`.
- **On a schedule with the Factory CLI (Linux and macOS):** `factory schedule on --project <name|path>` opts a registered project in on the branch it has checked out. It refuses a branch that `origin` lacks (as of your last fetch), a `dispatch.sh` that is not executable, and a `.sandcastle` copy whose `dispatch.mts`/`board.mts` predate launch reservations, so copy those in first. `factory schedule on` installs one `factory-tick` timer for all projects: a tick a minute after it starts, then 5 minutes after each tick finishes. Each tick visits opted-in projects one after another, a different one first each tick so none always takes the free slots first, and runs `dispatch.sh --max 3` for each as its own process group, with `FACTORY_SCHEDULED=1` (this dispatcher ignores it). A registered project that is not opted in instead gets `node .sandcastle/dispatch.mts --refresh-only --base <its checked-out branch>` each tick, read-only, so its cards stay current; a paused project gets nothing. This needs a copy whose `dispatch.mts` supports `--refresh-only` without `--ticket` (#93); an older one fails the refresh, which is logged and never fails the tick. There is no pass timeout, and under the service there is no terminal, so no image builds. systemd, not a Factory file, says whether scheduling is on. `factory schedule off` disables and stops the timer, then cancels the active tick: its pass and the shell, `npx` and analysis processes under it get SIGTERM (SIGKILL to that group only after 30 seconds), and no later project starts. A pass that exits while its own non-detached children still run has that group terminated the same way. Ticket runs this dispatcher already launched are detached into their own groups, so they keep going. `factory schedule off --project <name>` pauses one project, `factory schedule status` says why each project would or would not run and shows scheduler health and timings (also in `factory status`), `journalctl --user -u factory-tick` is the log, `~/.local/state/factory/scheduler/history.json` keeps the start, end, duration and result of the last 1000 passes and ticks (for judging any future timeout; nothing times out), and `factory uninstall` stops scheduling and then removes the units. On macOS the same commands drive one launch agent, `com.factory.tick`, running a supervisor that waits a minute, then runs a tick 5 minutes after each one finishes; launchd's enablement and running state say whether scheduling is on, `off` disables the label before `launchctl bootout` signals the supervisor (which cancels its pass the same way and exits successfully, so it is not restarted), and the log is `~/.local/state/factory/scheduler/tick.log`. Disable any legacy `sandcastle-dispatch@<name>.timer` below first; Factory lists them but never touches them. The [cutover runbook](../docs/scheduler-cutover.md) gives the order: remove legacy timers, refresh copies, opt in, arm. See the README's "On a schedule: `factory schedule`".
- **Jam report (Factory scheduler, #61).** When the Factory tick runs a pass it sets `FACTORY_JAM_REPORT` and `FACTORY_PASS_ID`; the pass then writes, before launching, whether the project is jammed (`findJam` in `graph.mts`: still-ready stopped tickets and the holds behind them, only when nothing is in flight, nothing launched, nothing awaits analysis and the shared cap has room) and each such ticket's requirement fingerprint. Manual and `--dry-run` passes write nothing, and the report changes nothing in the pass. The tick confirms a jam seen on two completed passes and starts a repair only when the copy has `prompt.recover.md` (not yet copied, #63). Copy `dispatch.mts` and `graph.mts` together.
- **On a schedule (Linux/systemd, legacy):** from the project, run `<sandcastle-helper>/orchestrator/install-dispatch.sh` (or pass the repo path, and `--name` if two repos share a folder name). It installs the template units `sandcastle-dispatch@.service` and `.timer` once, writes `~/.config/sandcastle/dispatch/<name>.env` (the repo path, and a PATH that reaches `node`, `glab`, `claude` and `docker`), and enables `sandcastle-dispatch@<name>.timer`. Each project gets its own timer; the base is the branch checked out in that repo. Each timer re-arms 5 minutes after its pass finishes, so a project's passes never overlap, and a random delay of up to 2 minutes keeps projects from reading the shared run cap at the same moment. List them with `systemctl --user list-timers 'sandcastle-dispatch@*'`, read a project's log with `journalctl --user -u sandcastle-dispatch@<name>`, remove one with `install-dispatch.sh --uninstall <name>`. Run `loginctl enable-linger $USER` so timers keep running when you log out. Replaces the old single-project `sandcastle-dispatch.service`/`.timer`; the installer tells you if one is still installed.

## Ticket graph

Each dispatcher pass works out which tickets can start, so that (a) a ticket doesn't start before the tickets it depends on are merged, and (b) two tickets touching the same files are never in progress at once. The graph lives in the state dir; GitLab issue links are neither read nor written.

- **Manifests.** For each candidate, a read-only `claude -p` (model in `GRAPH.model`; Read, Grep and Glob only) reads the ticket and the code at `origin/<base>` and writes `<stateDir>/graph/<project>--<iid>.json`: what the ticket provides, what it needs that the code doesn't have yet (and which open ticket creates it), and the paths it is likely to change. The analysis runs in a detached worktree under `<stateDir>/worktrees/`.
- **Catalogue.** Blockers can only be open tickets in `TRACKER.milestone`, or in the whole project when no milestone is set. With Tasks, an issue that has them is replaced by its open Tasks (even ones outside the milestone), so sibling Tasks can depend on each other and the parent itself is never a blocker.
- **When it re-analyses.** A manifest is cached on a hash of the ticket's title, description and comments (and, for a Task, its parent's title and description); Sandcastle's own comments (marked `<!-- sandcastle -->`) and label changes don't count. A ticket is re-analysed when that hash changes, when a ticket it depends on is edited, or when it needs something nobody provided and new tickets have appeared. At most `GRAPH.maxAnalysesPerPass` per pass. To fix a wrong blocker, edit the ticket text: the next pass re-analyses it.
- **Who can start.** Its manifest is current, every ticket it depends on is closed or has its Sandcastle branch merged into the base, and its paths don't overlap a live run. A run is live from start until its MR is merged or closed, not just until the MR opens. A live run's real diff replaces its predicted paths once the implementer commits. `GRAPH.conflictIgnore` lists paths whose overlap doesn't count. Dependency cycles are broken by ignoring the weakest edge (logged).
- **Implementer finds a missing prerequisite.** It writes `blocked.json` to the evidence dir instead of committing. If every blocker is an open, unmerged ticket, the run moves to `waiting`, its empty branch is deleted, and the dispatcher relaunches it once the blockers are satisfied. Otherwise (no ticket provides it, or that ticket is already merged or closed) the ticket gets `LABELS.needsHuman` and a comment.
- **Before the MR opens.** If the ticket was edited during the run, the MR says it was built from an older version, with the description diff. `git merge-tree` against other live Sandcastle branches lists any exact conflicts in the MR description.
- **`--dry-run`** runs the analysis (it costs model calls) and prints each ticket's decision without launching, touching the board, or closing and relabelling tickets.
- **Tests:** `node --test 'orchestrator/*.test.mts'` (Node 22.18+).
- **Model labels (personal config).** A unit of work without exactly one model label (`model:sonnet` or `model:opus`) stays `queued` on the board with the reason; add the label and the next pass picks it up. On a sub-issue the label goes on the sub-issue.

## Not included

No automatic retry of failed runs. Human-written MRs don't hold their files in the conflict check.
